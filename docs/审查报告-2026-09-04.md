### [中] 写入先完成、同步后落地时，刚记的那笔会消失、刚删的那条会复活

**位置** `src/lib/store.ts:209` ｜ **多久碰到** 几个月后（网速慢或流水变多、fetchAll 变慢时会更早、更频繁） ｜ **维度** 数据层正确性

**现象**：手机切回 App（触发后台同步）后立刻记一笔并保存：保存成功、云端已经存了，但一两秒后这笔从流水/首页消失。用户以为没记上，再记一遍 → 账本里出现两条重复。删除同理：切回 App 后立刻删一条，删除成功，随后这条又自己冒出来。我写了临时测试实测复现，两条断言都红：新增那笔落地后 transactions 是空数组，删除那条落地后又回到列表里。

**根因**：pendingTx/pendingCat 只挡住了「写还在飞、快照先回来」这一个方向。反方向没挡：refresh() 在 store.ts:136 发出 GET（此刻服务端还没有这笔），随后 addTx/editTx/removeTx 的 finally（store.ts:209 / 228 / 248，updateCategory 是 291）在写入成功的瞬间就把补丁删掉；等那份「比写入更早出门」的快照在 store.ts:143 落地时，补丁表已空，applyPending 原样放行，于是用一份过期快照覆盖了正确的本地状态。补丁的撤销时机看的是「写完了没」，而正确的判据是「有没有一次在写完之后才出门的同步回来过」。

**改法**：给同步加世代号，按世代退休补丁，而不是写完就删。store.ts 模块级加：let fetchSeq = 0 和 const settledAt = new Map<string, number>()。refresh() 里改成：const my = ++fetchSeq，再 await api.fetchAll()；拿到 snap 后、applyPending 之前先淘汰旧补丁：for (const [id, g] of settledAt) if (g < my) { pendingTx.delete(id); pendingCat.delete(id); settledAt.delete(id) }。addTx/editTx/removeTx/updateCategory 的 finally 里把 pendingTx.delete(id) 换成 settledAt.set(id, fetchSeq)（记下「写完时最后一次同步的世代」）；判据 g < my 的含义是「这次 GET 出门时该写入已经落库」，才允许丢补丁。另加一个 60 秒兜底 setTimeout 删补丁，避免长期不同步时补丁表越攒越多。同时把我这两条反向时序用例补进 src/lib/store.test.ts（先确认它们在改之前是红的）。

**★校验修正（以此为准）**：

世代号的思路对，但建议里"把 finally 的 delete 直接换成 settledAt.set"会引入一个新 bug，必须改掉。

问题出在**写入失败**的那条路。addTx 的 catch（store.ts:203-207）已经把这行从界面上撤掉并弹了"保存失败"，可 finally 照样执行——按建议改完，这个失败的补丁就留在 pendingTx 里不删了。此时那次还在飞的 refresh（世代 my == g，`g < my` 为假，不退休）落地，applyPending 会把这条**根本没存进云端**的记录重新塞回列表，还被 persist 写进缓存。用户明明看到"保存失败"，账本里却多出一笔幽灵记录。editTx 失败同理（回滚成旧值后又被补丁改回新值），removeTx 失败会把 DELETED 补丁留下，让那条已经回滚回来的记录再次消失。现在的 `finally { delete }` 恰好没有这个问题。

所以判据要收紧成"**写成功了**才按世代退休；写失败立刻删补丁"：

store.ts 模块级：
  let fetchSeq = 0
  const settledTx = new Map<string, number>()
  const settledCat = new Map<string, number>()   // 两张表分开，别用一个 map 同时删 pendingTx 和 pendingCat

refresh()（放在 133 的守卫之后、136 的 await 之前）：
  const my = ++fetchSeq
  const snap = await api.fetchAll()
  for (const [id, g] of settledTx) if (g < my) { pendingTx.delete(id); settledTx.delete(id) }
  for (const [id, g] of settledCat) if (g < my) { pendingCat.delete(id); settledCat.delete(id) }
  // 再 applyPending

addTx（editTx/removeTx 同形，去掉 finally）：
  try {
    await api.insertTx(t)
    settledTx.set(t.id, fetchSeq)                 // 成功：等一次"写完之后才出门"的同步回来再退休
    setTimeout(() => { pendingTx.delete(t.id); settledTx.delete(t.id) }, 60_000)   // 长期不同步的兜底
    return true
  } catch (e) {
    pendingTx.delete(t.id); settledTx.delete(t.id)  // 失败：立刻删，不能让失败的补丁被叠回去
    ...原来的回滚 / toast...
    return false
  }
updateCategory 用 pendingCat/settledCat 同样处理（注意它成功分支里的 get().persist() 保持不动）。

两个细节：
- `const my = ++fetchSeq` 放在守卫之后。放前面也不会漏（空转的世代只会让 g 偏大、补丁多留一会儿，方向是安全的），但放后面语义才是"每个真出门的 GET 一个号"。
- addCategory（store.ts:262-269）不走 finally，它靠 268 行的 `setTimeout(..., 10_000)` 删补丁，本身就是同一类隐患的弱化版；顺手把它也改成成功即 `settledCat.set(created.id, fetchSeq)` + 60 秒兜底，四个写入口径才一致。

测试：把我上面那两条反向时序用例补进 src/lib/store.test.ts（改之前是红的，已实测），另外一定要再加两条失败路径用例，专门盯这个新 bug：refresh 在飞 → addTx 抛错 → 快照落地，断言列表里**没有**这条；removeTx 抛错 → 快照落地，断言这条**还在**。

**校验依据**：断言逐条核对，全部属实，且我实测复现了两条。

1) 代码确实是那样写的。store.ts:136 `const snap = await api.fetchAll()`，落地在 141/143：`transactions: applyPending(snap.transactions, pendingTx)` → `set({ ...merged, ... })`。补丁的撤销确实在 finally 里、以"写完了"为判据：addTx 的 store.ts:208-210 `} finally { pendingTx.delete(t.id) }`，editTx 227-229、removeTx 247-249、updateCategory 289-291 同形。pending.ts:12 `if (pending.size === 0) return rows` —— 补丁表空时 applyPending 原样放行，正是报告说的"用过期快照覆盖本地状态"。

2) 上下文里没有反向保护。refresh 的守卫只有 store.ts:133 `if (get().syncing || get().auth !== 'in') return`，挡的是并发 refresh，不挡"refresh 在飞时发生写入"。addTx/removeTx 里没有任何 syncing 判断。

3) 路径可达。App.tsx:53 `if (document.visibilityState === 'visible') void refresh()`；store.ts:129 冷启动 `if (signedIn) await get().refresh()`；Settings.tsx:141 手动同步按钮。而 Entry.tsx:371 保存键只被 `disabled={busy || !online}` 挡，同步中照样能保存。api.ts:59-80 的 fetchAll 是"accounts+categories 并行 → 再翻页拉 transactions"，至少两个往返、流水过千还要多页，而 insertTx（api.ts:86-89）只有一个往返，写先完成完全正常。

4) 我在 src/lib/__rev.test.ts 复用 store.test.ts 的假 api 写了两条反向时序用例（跑完已删除，工作区干净）：
 - refresh 先出门 → addTx 成功 → 快照落地：`AssertionError: expected [] to include 't1'`
 - refresh 先出门 → removeTx 成功 → 快照落地：`AssertionError: expected [ 't1' ] to not include 't1'`
 两条都红，和报告一致。

严重度我降到"中"，因为后果不对称：
 - 新增那笔：云端已经写进去了，丢的只是本地列表 + 被 persist 写进缓存的那份（store.ts:144）。下次同步会回来。但在回来之前用户看到的就是"没记上"，重记一遍就在云端留下两条真重复，要手工删——这一半是真损失。
 - 删除那条：复活只发生在本地，云端已经删掉了，下次 refresh 自己消失；再删一次 `delete().eq('id', id)` 命中 0 行也不报错。纯界面惊吓，无数据后果。
 触发还要求"写完早于快照回来"且"快照出门早于该行落库"这两件事同时成立，窗口是秒级，不是天天遇到。

### [中] 备份 JSON 恢复到重建后的库必然失败，一条都导不进去

**位置** `src/lib/api.ts:125` ｜ **多久碰到** 几年后（只在换库/重建后恢复备份时触发，但那正是最不能失败的时刻） ｜ **维度** 数据层正确性

**现象**：真出事那天（误删数据、Supabase 项目被删或换项目）按 README 的路子恢复：新建项目 → 跑 0001_init.sql → 设置页导入备份 JSON。结果弹「导入失败：已有同名分类」，账户、分类、流水一条都没进去，界面还是空的。唯一的备份手段在最需要它的时刻不可用，用户只能手工写 SQL。

**根因**：importAll 三处 upsert 都写死 onConflict: 'id'（api.ts:125/129/132），只处理主键冲突。但 accounts 上还有 unique (user_id, name)（0001_init.sql），categories 上还有 cat_root_uniq (user_id, kind, name) 和 cat_child_uniq (user_id, parent_id, name)。0001 的预置数据块会用**新 id** 建出同名的 4 个账户和全部分类，备份里的行 id 是旧的、名字一样 → INSERT ... ON CONFLICT (id) 不认名字这个唯一索引 → 直接抛 23505。第一句 accounts 就炸，后面全不执行；friendlyError（api.ts:48）把 23505 一律翻成「已有同名分类」，连报错都指错了地方。

**改法**：两步。(1) 立刻可做的最小改动：importAll 开头先 fetchAll 拿到库里现有的 accounts/categories，按 name（分类按 kind+parent 名字路径）建 旧id→现有id 的映射，把 snap 里冲突的行 id 改写成现有 id，并同步改写 categories.parent_id 和 transactions 的 account_id / to_account_id / category_id，再走现在的 upsert。(2) 更彻底的做法：新增 supabase/migrations/0004_restore.sql，写一个 restore_snapshot(payload jsonb) 函数（security invoker，走 RLS），在**一个事务**里先删当前用户的 transactions→categories→accounts 再整份插入，api.ts 的 importAll 改成调这个 rpc；顺带解决下面那条非事务问题。另外把 friendlyError 里 23505 的文案改成「已有同名的账户或分类」，别只说分类。

**★校验修正（以此为准）**：

建议改法方向对，但两步都有坑，按下面改：

【fix (2) 有实打实的 bug，照抄会把所有金额放大 100 倍】报告写「api.ts 的 importAll 改成调这个 rpc」，如果直接把 `snap` 当 jsonb payload 发过去就违反铁律 1。现在的 importAll 在 135 行 `const rows = snap.transactions.map(txToRow)`，txToRow（api.ts:32）里 `amount: centsToDb(t.amount)` 才把整数「分」变成 numeric 字符串；备份 JSON 里存的是内存快照，amount 是整数分（csv.ts buildJson 直接塞 snap.transactions，不做转换）。一笔 12.50 元在 JSON 里是 1250，直接进 numeric(12,2) 就变成 1250.00 元。所以走 rpc 也必须先 `snap.transactions.map(txToRow)` 再 JSON.stringify，或者在 SQL 函数里除以 100（不推荐，多一个转换点，违反「只有 money.ts 做元↔分转换」）。

【fix (1) 的 id 重映射方案对，但要补三条】(a) 分类映射键必须是 kind + 父名路径：cat_root_uniq 是 (user_id, kind, name)，所以支出的「其他」和收入的「其他」是两行，只按 name 映射会把它们并成一行，然后同一批 upsert 里出现重复 id，Postgres 报 21000「ON CONFLICT DO UPDATE command cannot affect row a second time」，换个错继续失败。(b) 重映射后必须同步改 categories.parent_id、transactions.account_id / to_account_id / category_id（报告写了，别漏），否则子分类会撞 trg_cat_depth 的「父分类不存在」。(c) 名字对不上的行（比如用户把「中国银行」改名成「中行」再备份）不会被映射，会当新行插入，结果库里 4 个预置账户 + 备份账户并存、分类也翻倍，界面一堆没用过的空分类。

【对这个项目最划算的改法，优先于上面两条】不要在 importAll 里做名字猜测，直接把「恢复」做成显式的整库覆盖：
1. api.ts 加 `export async function wipeAll()`：按 transactions → categories → accounts 顺序各发一条 delete（用 `.neq('id', '00000000-0000-0000-0000-000000000000')` 之类的全匹配条件，PostgREST 不允许无条件 delete；RLS 保证只删自己的行）。顺序不能反，因为 transactions.category_id / account_id 都是 `on delete restrict`。
2. Settings.tsx 里把现在这一个入口拆成两个：保留「合并导入（同 ID 覆盖）」，新增「整库恢复（先清空再导入）」，后者的 confirm 文案写清楚「会先删除当前 N 个账户 / N 个分类 / N 条流水，再按备份文件重建」。这样用户点哪个都知道自己在干什么，也不会有人误点整库恢复丢掉备份之外的新数据。
3. api.ts:48 的文案改成 `'已有同名的账户或分类'`。
4. README 第 150 条后面补一句真正的恢复步骤（新建项目 → 建账号 → 跑 0001 → 登录 → 设置页「整库恢复」），并且这条路径必须实测一次：现在 README 里根本没写过恢复步骤，这个 bug 之所以三个月没被发现，就是因为从来没人走过一遍。

至于 0004_restore.sql 的事务版 rpc，是更干净，但对这个只有一个用户、一次几千行的库，收益不足以抵掉「多一个 SQL 迁移 + 金额转换点要盯」的复杂度。真要做，函数体里只接已经转成 numeric 字符串的 payload，别在 SQL 里碰分/元换算。

**校验依据**：断言逐条核对，全部属实。

1) 代码确实是那样写的。api.ts:125 `const acc = await supabase.from('accounts').upsert(snap.accounts, { onConflict: 'id' })`，126 行 `if (acc.error) throw acc.error`；129 行 parents、132 行 children、137 行 transactions 也都是 `{ onConflict: 'id' }`。importAll 全函数（124-140）没有任何先清库、先按 name 查映射的保护，第一句就是 accounts upsert。

2) 唯一约束确实存在。0001_init.sql accounts 表定义末尾 `unique (user_id, name)`；categories 下面 `create unique index if not exists cat_child_uniq on public.categories (user_id, parent_id, name) where parent_id is not null;` 和 `cat_root_uniq on public.categories (user_id, kind, name) where parent_id is null;`。

3) 预置数据确实会用新 id 造出同名行。0001 末尾 `do $$` 块里 `insert into public.accounts (user_id, name, kind, sort) values (uid,'中国银行','bank',1),(uid,'招商银行','bank',2),(uid,'支付宝','wallet',3),(uid,'微信','wallet',4)` —— 没写 id，走 `default gen_random_uuid()`；分类同理，5 个支出大类 + 28 个二级 + 6 个收入分类。而备份 JSON 里带的是旧 id（csv.ts 的 parseImport 只 `delete copy.user_id` / `delete copy.updated_at`，id 原样保留）。PostgREST 的 upsert 生成 `INSERT ... ON CONFLICT (id) DO UPDATE`，ON CONFLICT 只认括号里那一个索引，撞上 accounts_user_id_name_key 会直接抛 23505 而不是转成 UPDATE。所以「新项目 → 跑 0001 → 导入备份」这条路 accounts 第一句就炸，后面 categories / transactions 全不执行，界面还是空的。

4) 报错文案确实指错地方。api.ts:48 `if (code === '23505' || /duplicate key/i.test(msg)) return '已有同名分类'`，Settings.tsx:90 `showToast(\`导入失败：${friendlyError(e)}\`)` —— 账户冲突也会显示「导入失败：已有同名分类」。

5) 这条路径可达且是唯一路径。Settings.tsx:168 有「从 JSON 备份导入 / 恢复」入口 → importJson → store.ts:308 importSnapshot → api.importAll；README:150 白纸黑字写「Supabase 免费版无自动备份，误删有无还原点。靠设置页导出 JSON」。除此之外没有第二种恢复手段。

需要降级的两点（所以判「中」不判「高」）：
- 不是所有恢复场景都失败。同一个库里误删流水后重新导入，accounts/categories 的 id 没变，onConflict:'id' 走 DO UPDATE 正常，流水能全部回来。只有「换库/重建后」这一支才必挂，报告自己也限定了这个前提。
- 「只能手工写 SQL」夸大了工作量，也没有数据丢失：备份 JSON 本身完好，在 SQL Editor 里跑三行 `delete from public.transactions; delete from public.categories; delete from public.accounts;` 再导入就能全量恢复（父分类在 129 行先插、子分类在 132 行后插，trg_cat_depth 的顺序要求满足；tx_shape / tx_category_kind_guard 也都满足）。对编程小白来说这仍然是「自己搞不定」，但不是不可逆。

### [中] 开户时录的余额被统计成「有收入没记」

**位置** `src/lib/compute.ts:299` ｜ **多久碰到** 今天 ｜ **维度** 统计与计算

**现象**：项目没有「初始余额」字段（CLAUDE.md 第 17 行），账户页也明说「从未核对，点此输入实际余额」。所以用户第一次把中国银行的 15000 元录进去时，写下的是一条 adjust +1500000 分。之后打开统计页最底下那张卡，永远显示「累计未记录差额 +¥15,000.00」，下面配一行「正数说明有收入没记」。用户会一直以为自己有一万五的收入忘了记，而且这个数字永远不会消掉——除非把开户那笔校准删了，但删了账户余额又归零。开户当月还会额外污染「本月未记录差额」。

**根因**：adjustTotal 无差别地把所有 type==='adjust' 的记录相加。但 adjust 在本项目里承担了两种完全不同的语义：(a) 开户时的初始余额录入，(b) 事后核对发现的漏记差额。只有 (b) 才是「未记录差额」，(a) 是本金。compute.ts:299-303 没做区分，Stats.tsx:405-414 又给这个和加了一句断言式的解读文案。

**改法**：让 adjustTotal 排除每个账户的「开户余额」——即该账户名下按 (date, created_at) 排序最早的那笔记录，如果它是 adjust 就跳过（事后才做的校准不会是账户第一笔，不会被误伤）：

export function adjustTotal(txs: Transaction[], ym?: string): number {
  const firstAdjust = new Map<string, string>() // accountId -> 该账户最早一笔的 tx id
  const firstKey = new Map<string, string>()
  const k = (t: Transaction) => `${t.date}T${t.created_at}`
  for (const t of txs) {
    for (const id of [t.account_id, t.to_account_id]) {
      if (!id) continue
      const prev = firstKey.get(id)
      if (!prev || k(t) < prev) {
        firstKey.set(id, k(t))
        firstAdjust.set(id, t.type === 'adjust' ? t.id : '')
      }
    }
  }
  const opening = new Set([...firstAdjust.values()].filter(Boolean))
  let s = 0
  for (const t of txs) {
    if (t.type !== 'adjust' || opening.has(t.id)) continue
    if (ym && !inMonth(t, ym)) continue
    s += t.amount
  }
  return s
}

同时把 Stats.tsx:414 的说明改成「来自余额校准（不含开户时录入的初始余额）：负数说明有支出没记，正数说明有收入没记。」

**★校验修正（以此为准）**：

不要靠「排序猜语义」，要在写入时就把它标出来，这样用户在流水里看得见、也能自己改。

### [高] 默认账户 effect 会覆盖编辑回填，改一笔旧账会把钱挪到中国银行

**位置** `src/pages/Entry.tsx:112` ｜ **多久碰到** 几个月后（每换一台设备/一个浏览器、每次清站点数据后的第一次编辑必现） ｜ **维度** 记账主路径页面

**现象**：在一台"没有在这台设备/这个浏览器里存过账"的机器上（新电脑、新手机，或同一部 iPhone 上 Safari 与主屏 App 之间——README 坑 #8 说过两者存储是隔离的），从流水页点开一条旧记录：账户那排显示的是「中国银行」，不是这笔真正的账户（比如微信）；如果是转账，两端会显示成「中国银行 → 招商银行」。此时哪怕只是改个备注点「更新」，这笔钱就被挪到中国银行了，首页的账户余额随之全错，而且没有任何提示。

**根因**：第 80-104 行的"编辑回填" effect 和第 111-115 行的"默认值兜底" effect 在同一次提交里先后执行。回填 effect 先 setAccountId(这笔的真实账户)、setAccountTouched(true)，但兜底 effect 读到的是本次渲染的旧闭包值（accountId=null、accountTouched=false），于是又排队了一次 setAccountId(accounts[0].id)，排在后面的赢。平时不出事是因为 jz_entry_memory_v1 里存着上次用的账户，accountId 不为 null 把兜底挡住了；新设备上这份记忆是空的，挡不住。fromId / toId 同理（新设备上 mem.fromId 为 null）。

**改法**：给兜底 effect 加一句编辑态短路——编辑态的账户由回填负责，默认值不许插手：
useEffect(() => {
  if (editId) return
  if (!accountId && !accountTouched && accounts.length) setAccountId(accounts[0].id)
  if (!fromId && accounts.length) setFromId(accounts[0].id)
  if (!toId && accounts.length > 1) setToId(accounts[1].id)
}, [editId, accounts, accountId, accountTouched, fromId, toId])
验证：浏览器里清掉 jz_entry_memory_v1（或换个无痕窗口登录），从流水页点开一笔微信的支出，账户那排必须高亮微信。

**★校验修正（以此为准）**：

用一个「回填是否已完成」的 state 门（不能用 loadedEdit 这个 ref —— 它在回填 effect 里被同步改掉，同一帧的兜底 effect 立刻就能读到新值，门形同虚设）：

// 第 77 行附近

// 回填 effect 末尾（第 103 行 `}` 之后、第 104 行依赖数组之前）补一句

// 兜底 effect 改成
useEffect(() => {
  if (!backfilled) return
  if (!accountId && !accountTouched && accounts.length) setAccountId(accounts[0].id)
  if (!fromId && accounts.length) setFromId(accounts[0].id)

为什么比 `if (editId) return` 好：backfilled 是 state，回填那一帧它还是 false，兜底被完整跳过；下一帧变 true 时 accountId / fromId / toId 已经是这笔的真实值，三个 if 自然不成立，不会再覆盖。而那些回填没碰到的槽位（编辑支出时的 fromId/toId、编辑转账时的 accountId）仍会被填上默认值，用户中途切类型不会遇到空白 chip。新增记账（editId 为 null）时 backfilled 初值就是 true，行为完全不变。

**校验依据**：逐句核对后成立，代码就是那样写的，且没有任何保护。

### [中] 没信号时点「强制刷新」会把 App 变成打不开的白屏

**位置** `src/lib/sw.ts:12` ｜ **多久碰到** 几个月后 ｜ **维度** 外壳与平台

**现象**：在地铁、电梯、飞机上或 github.io 被卡的时候，用户觉得 App「卡住了/数据不对」，去设置页点「强制刷新（拿最新版本）」→ 确认 → 屏幕变白，出现「Safari 打不开该网页，因为无法连接到服务器」。此后反复打开主屏图标都是这个页面，直到重新联网为止。原本装了 Service Worker 时离线也能打开看账本，这一下把离线能力也一起删了。

**根因**：hardReload() 的顺序是「先注销 SW（15–17 行）→ 再删掉所有 caches（18–21 行）→ finally 里 location.reload()（23 行）」。注销和清缓存都是本地操作、一定成功，但重新加载要走网络。一旦网络不通，页面拿不到 index.html，而能兜底的 SW 和预缓存已经被自己亲手删掉了，App 就没有任何本地副本可用。

**改法**：改成「先确认能拿到新文件，再动缓存」。在 src/lib/sw.ts 的 hardReload 开头加：`if (!navigator.onLine) throw new Error('当前离线，联网后再试')`，再加一次探测 `const r = await fetch(location.href, { cache: 'reload' }); if (!r.ok) throw new Error('暂时连不上服务器，稍后再试')`，探测通过之后才执行现有的注销 + 清缓存 + reload。调用处 src/pages/Settings.tsx:186-189 把 `await hardReload()` 包进 try/catch，失败时 `showToast(friendlyError(e))`，并把确认框文案改成「清空程序缓存并重新加载？需要联网，账本数据和登录状态不受影响。」

**★校验修正（以此为准）**：

原建议的探测 `const r = await fetch(location.href, { cache: 'reload' })` 是无效的，照抄会得到「改了等于没改」：此时 SW 还没注销，请求会被 workbox 预缓存路由拦下。node_modules/workbox-precaching/PrecacheRoute.js:40-51 的 match 只看 `request.url`，不看 `request.mode`（navigateFallback 那条 NavigationRoute 才只认 navigate）；node_modules/workbox-precaching/utils/generateURLVariations.js:20-30 会先 `urlObject.hash = ''` 再对结尾是 '/' 的路径拼上 directoryIndex('index.html')。所以 HashRouter 下的 `location.href`（.../jizhang/#/settings）被规约成 .../jizhang/index.html，正好是预缓存里的条目，**完全断网时也会命中缓存返回 200**，`cache: 'reload'` 只影响 HTTP 缓存、管不到 SW。探测必然通过，白屏照旧。

正确改法（关键是让探测 URL 无法命中预缓存路由，从而真的落到网络）：

src/lib/sw.ts：
```ts
export async function hardReload(): Promise<void> {
  // 先确认真能从网络拿到文件，再动缓存。探测 URL 必须带一个随机参数：
  // workbox 预缓存路由是按 URL 匹配的，直接 fetch(location.href) 会命中缓存里的
  // index.html，断网时也返回 200，探测就白做了。默认只有 utm_*/fbclid 会被忽略，
  // 所以 _probe 这个参数能保证不匹配任何路由、直落网络。
  const probe = new URL(location.href)
  probe.hash = ''
  probe.searchParams.set('_probe', String(Date.now()))
  let ok = false
  try {
    const r = await fetch(probe.href, { cache: 'no-store' })
    ok = r.ok
  } catch {
    ok = false
  }
  if (!ok) throw new Error('连不上服务器，联网后再试')

  try {
    if ('serviceWorker' in navigator) {
      const regs = await navigator.serviceWorker.getRegistrations()
      await Promise.all(regs.map((r) => r.unregister()))
    }
    if ('caches' in window) {
      const keys = await caches.keys()
      await Promise.all(keys.map((k) => caches.delete(k)))
    }
  } finally {
    location.reload()
  }
}
```
注意 throw 必须在 try/finally **之外**，否则 finally 里的 location.reload() 照样执行，等于没拦。`navigator.onLine` 那道前置判断可加可不加（连着没有外网的 WiFi 时它仍是 true，挡不住），真正起作用的是上面这次带随机参数的探测；要加就只当作一个更快的提前返回，不能拿它当唯一保护。

src/pages/Settings.tsx:186-189 调用处要接住异常（friendlyError 已在该文件第 5 行 import，不额外破坏分层）：
```tsx
onClick={async () => {
  if (!window.confirm('清空程序缓存并重新加载？需要联网，账本数据和登录状态不受影响。')) return
  try {
    await hardReload()
  } catch (e) {
    showToast(friendlyError(e))
  }
}}
```
改完的用户可见效果：没信号时点「强制刷新」→ 底部弹一条「连不上服务器，联网后再试」，页面原地不动，离线照样能看账本。

**校验依据**：断言逐条核对属实。src/lib/sw.ts:12-25 原文就是「先注销 SW（14-17 行 getRegistrations().unregister()）→ 再删所有 caches（18-21 行 caches.keys()/caches.delete）→ finally 里 location.reload()（22-24 行）」，中间没有任何联网判断。入口真实可达：src/pages/Settings.tsx:186-189 的「强制刷新（拿最新版本）」行 onClick 里 `if (window.confirm('清空程序缓存并重新加载？账本数据和登录状态不受影响。')) await hardReload()`，既没有 disabled，也没提示需要联网——src/lib/hooks.ts:15 的 useOnline 只被 src/pages/Entry.tsx:54 用了，设置页完全没用。离线能力确实只靠 SW：vite.config.ts 里 VitePWA 配了 `globPatterns: ['**/*.{js,css,html,png,svg,ico,woff2}']` + `navigateFallback: 'index.html'`，而 SW 只在 src/App.tsx:18 的 useRegisterSW 里注册——页面加载不出来就永远不会重新注册，所以「注销+清缓存后离线 reload」确实会卡在无法连接页，且不会自愈。后果描述没有夸大反而是准确的：账本数据存在 localStorage（src/lib/store.ts:35 `localStorage.setItem(CACHE_KEY, json)`），caches.delete 动不到它，登录态也在 localStorage，所以只丢「离线可打开」这一项，联网后重新打开即恢复。用户看到的现象就是：在地铁/电梯里点了这个按钮 → 白屏「Safari 打不开该网页」→ 反复点主屏图标还是这页 → 一有信号再打开就全好了，一条账也不会少。严重度按「必须自己主动去设置页点一个冷门按钮 + 恰好没网 + 联网即自愈 + 零数据损失」降为中。但建议改法本身有硬伤（见 corrected_fix）：那次探测在离线时也会返回 200。

### [中] 记账页停留过夜，第二天记的第一笔会落到昨天

**位置** `src/pages/Entry.tsx:70` ｜ **多久碰到** 几天内，只要有一天是在记账页退出的 ｜ **维度** 完整性批评

**现象**：新增记录保存后页面不跳走，所以「记一笔」几乎总是你退出 App 时停留的那一页。iOS 主屏 App 是挂起不是关闭，第二天点图标回来还是这一页，date 状态还是昨天。此时输金额直接点保存，这笔就写进了昨天：流水页出现在昨天那组里，昨天的日小计和月合计都多一笔，今天的「今日开支」少一笔。保存成功后第 230 行会把 date 重置成当时的 today()，所以只有当天第一笔是错的，之后正常——正因为它自己会好，很难被发现是规律性问题。日期胶囊此时会显示「昨天」并高亮，但用户默认它是「今天」，不会去看。

**根因**：date 用 useState(today()) 只在组件挂载时算一次，而这一页在 App 被挂起/恢复期间始终没有卸载，也没有任何地方在回到前台时重算日期。App.tsx 的 visibilitychange 只触发 refresh()，不碰页面里的日期状态。

**改法**：在 Entry 里加一个「用户是否手动改过日期」的标记（仿照现有的 accountTouched）：const [dateTouched, setDateTouched] = useState(false)，DatePicker 的 onPick 里置 true；再加一个 effect，监听 document 的 visibilitychange，可见且 !dateTouched 时 setDate(today())；save() 成功后把 dateTouched 重置成 false。改动只在 Entry.tsx 内，不影响别的页面。

**★校验修正（以此为准）**：

建议的改法方向对，但**漏了编辑态，会造成比原 bug 更严重的静默改数据**：

编辑一条旧记录时，日期是第 86 行 `setDate(editing.date)` 灌进去的，用户并没有碰 DatePicker，所以 `dateTouched` 仍是 `false`。此时用户切出去看一眼微信再切回来（visibilitychange 在切 App、锁屏、切标签页都会触发，不需要跨天），effect 就会把 `date` 悄悄改成 `today()`；用户点「更新」，那条上周的记录日期就被改成今天了 —— 用户不知情，且原日期已丢。这比「今天第一笔记到昨天」严重。

正确改法（仍然只动 Entry.tsx）：

```ts
const [dateTouched, setDateTouched] = useState(false)

// 挂起过夜后回到前台，把没被手动改过的日期滚到新的今天。
// 编辑态绝不能动：那里的日期是记录本身的日期，不是「今天」。
useEffect(() => {
  if (editId) return
  const onVisible = () => {
    if (document.visibilityState !== 'visible' || dateTouched) return
    const t = today()
    setDate((d) => (d === t ? d : t))
  }
  document.addEventListener('visibilitychange', onVisible)
  return () => document.removeEventListener('visibilitychange', onVisible)
}, [editId, dateTouched])
```

配套三处：
1. `DatePicker` 的 `onPick` 从 `setDate` 换成 `(d) => { setDateTouched(true); setDate(d) }`（第 368 行）。
2. `save()` 第 230 行 `setDate(today())` 后面补一行 `setDateTouched(false)` —— 否则用户手动记过一笔昨天的账之后，这页就永久停止跟随日期了。
3. `editId` 作为依赖，保证从「新增」切到「编辑」（URL 带 id）时监听会摘掉。

注意 `setDate((d) => (d === t ? d : t))` 这个函数式写法不是洁癖：每次切回前台 App.tsx 的 `refresh()` 都会刷 store，Entry 本来就要 re-render，日期没变时不再多触发一次 setState。

**校验依据**：断言逐条核对，全部属实：

1. `src/pages/Entry.tsx:70` 就是 `const [date, setDate] = useState(today())` —— `useState` 的初值只在挂载时求一次，之后再没有任何地方重算。

2. 保存新记录后不跳页：`save()` 里只有编辑分支会 `nav(-1)`（第 212-216 行 `if (editing) { showToast('已更新'); nav(-1); return }`），新增分支走到第 224-231 行只做 `showToast(...)` / `setAmount('')` / `setNote('')` / `setDate(today())` / `setMore(false)`，页面留在 `/add`。所以「记一笔」确实是最容易被停留的那一页（TabBar.tsx 里 `/add` 就是中间那个大加号）。

3. 路由结构佐证组件不会被卸载：`App.tsx:101` 的 `{ path: 'add', element: page('记一笔', <Entry />) }`，只要不导航离开，Entry 一直挂载；iOS 主屏 App 挂起再恢复不触发卸载。

4. 前台恢复时确实没人碰日期：全项目 grep `visibilitychange` 只有两处，都在 App.tsx —— 第 23 行是 `void r.update()`（查 SW 更新），第 51-57 行 `onVisible` 只 `void refresh()`。Entry.tsx 里没有任何 visibilitychange/pageshow 监听。

5. 第 230 行 `setDate(today())` 确认存在，所以只有跨天后的第一笔会错，之后自动恢复正常 —— 「自己会好、难被发现」这个描述成立。

6. 后果链也对：`Home.tsx:30` 的 `const td = today()` 在 render 时算，所以今天的「今日开支」确实少这一笔；流水/月合计按 `tx.date` 归组，这笔落进昨天。

【但严重度要降级，理由是代码里有两处现成的可见提示】
- `Entry.tsx:356`：`className={\`chip ${date !== today() ? 'on' : ''}\`}` 和 `{fmtDateRel(date)}`，`today()` 是每次 render 现算的。用户按下第一个数字键就会 `setAmount` 触发 render，此刻日期胶囊立刻变成高亮的「昨天」，就摆在保存键上方。

所以是真 bug，但属于「界面已给出提示、用户没看、且可一键改回」的量级，不是高危。触发频率也比声称的低一档：iOS 独立 PWA 经常被系统整个杀掉重载（重载后 hash 还是 `#/add`，但 Entry 重新挂载，`today()` 重算，日期是对的），只有「挂起-恢复」这条路径才中招。

### [低] 导入中途失败会留下半截数据，界面还显示旧数据

**位置** `src/lib/store.ts:308` ｜ **多久碰到** 几年后（只在导入/恢复时触发） ｜ **维度** 数据层正确性

**现象**：导入几千条流水时网断了（或某一批违反了数据库约束）：弹「导入失败：网络不通」，但屏幕上的流水、余额还是导入前的样子，看起来像什么都没发生。实际上云端已经写进去了一部分（比如前 2500 条）。用户此时如果去手动补录，就会和已经进库的那部分打架；等下次切回 App 自动同步，才突然冒出一堆半截数据。

**根因**：importSnapshot 是 await api.importAll(snap) 然后 await get().refresh()（store.ts:309-310），失败时异常直接抛给 Settings.tsx:87，refresh() 那行根本不执行，本地状态没有被拉齐。而 importAll 本身是多条独立语句（api.ts:125 accounts、129 父分类、132 子分类、136-139 每 500 条一批的流水循环），没有事务，任何一批失败前面的都已经提交，也没有回滚。

**改法**：store.ts 的 importSnapshot 改成 try { await api.importAll(snap) } finally { await get().refresh() }——不管成功失败都把界面拉到云端的真实状态，用户至少看得见实际进了多少。Settings.tsx 的失败文案补一句「已导入的部分不会自动撤销，请再导入一次同一个文件（同 ID 会覆盖，重复导入是安全的）」，因为现在全是 upsert-by-id，重试确实幂等。彻底方案见上一条的 restore_snapshot 事务函数。

**★校验修正（以此为准）**：

建议的改法方向正确（try/finally 里 refresh），且不会引入新 bug：refresh() 自己在 store.ts:132-152 内部 try/catch 全吞了异常（失败只 set syncFailed），所以 finally 里的 refresh 不会顶掉 importAll 原来的错误，Settings 的「导入失败：xxx」照样弹。

但有一个坑要补：refresh 第 133 行 `if (get().syncing || get().auth !== 'in') return` 是个静默早退。手机上选文件会把 App 切到后台，返回时 App.tsx:53 的 visibilitychange 触发一次 refresh，几千条流水的 fetchAll 分页拉取可能还在飞，此时 finally 里的 refresh 会直接 return，界面照样停在旧数据——修了个寂寞。所以要么等它退出 syncing 再拉，要么把「强制拉一次」的语义显式表达：

```ts
async importSnapshot(snap) {
  try {
    await api.importAll(snap)
  } finally {
    // importAll 是每 500 条一批、逐批提交的，失败时前面的批次已经在云端了。
    // 不管成败都把界面拉到云端真实状态，否则用户看到的是「什么都没发生」。
    // 注意 refresh 在 syncing 时会静默早退（切回前台那次同步可能还在飞），等它结束再拉。
    for (let i = 0; i < 40 && useStore.getState().syncing; i++) {
      await new Promise((r) => setTimeout(r, 250))
    }
    await get().refresh()
  }
}
```

Settings.tsx:89 的文案也照建议补一句，对小白最关键：
```ts
showToast(`导入失败：${friendlyError(e)}。已导入的部分不会自动撤销，重新导入同一个文件是安全的（同 ID 覆盖）`)
```
注意 showToast 只显示 5 秒（store.ts:319），这句话偏长，更好的做法是在 Settings 里用一块常驻的红色提示条显示导入失败信息，而不是塞进一闪而过的 toast。

彻底方案仍是数据库端一个 restore_snapshot 的 plpgsql 函数，把删+插放进一个事务里，前端一次 rpc 调用——那才是真正的「要么全进要么全不进」。

**校验依据**：逐条核对，四条断言全部属实，没有找到反证。

1）store.ts:308-311 确实就是这么写的，没有任何保护：
```
async importSnapshot(snap) {
  await api.importAll(snap)
  await get().refresh()
},
```
importAll 抛错，第 310 行的 refresh() 就不执行，store 里的 accounts/categories/transactions 一个字节都没动（导入路径没有任何本地乐观写入），persist() 也没被调用，所以 localStorage 缓存也是旧的。

2）api.ts:124-140 的 importAll 确实是多条独立语句、无事务、无回滚：125 行 accounts upsert、129 行父分类、132 行子分类、136-139 行 `for (let i = 0; i < rows.length; i += 500)` 每批一次 upsert，每次 `if (error) throw error` 直接抛出。supabase-js 每个 upsert 是一次独立 HTTP 请求 = 一个独立事务，前面提交过的批次不会因为后面失败而撤销。

### [中] 同步请求若一直不返回，此后整个会话的同步被静默丢弃

**位置** `src/lib/store.ts:133` ｜ **多久碰到** 几个月后（信号差 + 后台切换时） ｜ **维度** 数据层正确性

**现象**：地铁里信号断续时切回 App，首页右上角「同步中…」一直挂着不消失；之后不管切走切回多少次、在另一台设备上记了多少笔，这台手机都再也拉不到新数据，设置页的「上次同步」时间永远停在旧值，也不报错。只有杀掉 App 重开才恢复。

**根因**：refresh() 第一行 if (get().syncing || ...) return 是一把没有超时的锁；syncing 只在 finally（store.ts:149-151）里放开，而 finally 要等 api.fetchAll 的 promise 落地才执行。fetchAll（api.ts:58-80）用的是 supabase-js 默认的 fetch，没有 AbortSignal、没有超时；iOS 在后台冻结页面时正在飞的请求可能永远不 settle。于是 syncing 永久为 true，后面每一次 visibilitychange 触发的 refresh（App.tsx:53）都在第一行被丢掉，而且是无声丢掉——syncFailed 也不会被置上，用户看不到任何异常提示。

**改法**：给读请求加超时和中止：api.ts 的 fetchAll 加一个 signal 参数，内部每个 supabase 查询带 .abortSignal(signal)；store.ts 的 refresh 里 const ac = new AbortController(); const t = setTimeout(() => ac.abort(), 20_000)，await api.fetchAll(ac.signal)，finally 里 clearTimeout(t)。这样超时会走 catch 分支，syncFailed 置上、锁正常释放。再加一道保险：把 syncing 换成记开始时间的 syncingSince: number | null，refresh 的守卫改成「正在同步且距开始不足 30 秒才跳过」，超过 30 秒视为上一次已经死了，允许重新发起。

**★校验修正（以此为准）**：

建议的第一部分（AbortController + 超时 + 每个查询挂 .abortSignal）方向正确，postgrest-js 也确实支持（PostgrestTransformBuilder.ts:642 `abortSignal(signal: AbortSignal): this`）。但原改法有两个坑，要按下面修正：

坑一：超时报错会给用户看英文。abort 抛出的是 AbortError，message 类似 "The operation was aborted."。api.ts:42-53 的 friendlyError 没有任何一条规则命中它，最后落到 :53 `return msg || '未知错误'`。首次打开 App 就超时时，走 store.ts:148 `if (!get().loaded) get().showToast(...)`，用户会看到一句英文报错。必须在 friendlyError 里加一条（放在 :47 那条网络规则旁边）：
`if ((e as { name?: string })?.name === 'AbortError' || /abort/i.test(msg)) return '网络太慢，同步超时'`

坑二：原建议的「保险」——把 syncing 换成 syncingSince、超过 30 秒就允许重新发起——如果单独加，会引入新 bug。两次 refresh 会并行：旧的那次万一后来settle 了，会在新的之后执行 store.ts:143 的 `set({ ...merged, lastSync: nowIso(), syncFailed: false })`，用一份更旧的快照盖掉刚拉回来的新数据（pending 补丁只保在途写入，保不住这个），而且它的 finally（:150）会把还在飞的那次的锁提前放掉。正确写法是给每次 refresh 编号，只让「当前这一轮」有权落地和放锁：

```ts
let runId = 0
// refresh 内：
const my = ++runId
const ac = new AbortController()
const t = setTimeout(() => ac.abort(), 20_000)
try {
  const snap = await api.fetchAll(ac.signal)
  if (my !== runId) return              // 已被更新的一轮取代，丢弃这份旧快照
  ...set(...)
} catch (e) {
  if (my !== runId) return
  set({ syncFailed: true }); ...
} finally {
  clearTimeout(t)
  if (my === runId) set({ syncing: false })
}
```
守卫那一行相应改成「syncingSince 存在且距今不足 30 秒才 return」。

另外两点实现细节：
- api.ts:58 改成 `fetchAll(signal?: AbortSignal)`，三处查询都要挂 `.abortSignal(signal)`（accounts、categories，以及 :68-76 分页循环里的 transactions；漏掉循环里那个，最容易卡住的恰恰是它）。参数设为可选，store.test.ts 里现有的 fetchAll mock 不用改。
- 20 秒的计时器覆盖的是整个 fetchAll（含分页多轮请求），流水上万条时正常拉取也可能被误砍。稳妥做法是每轮请求各起一个 20 秒超时，或把总超时放到 30-40 秒。

**校验依据**：逐句核对，断言全部属实，没找到反例。

1) 锁确实存在且无超时。store.ts:132-152 原文：
```

  if (get().syncing || get().auth !== 'in') return   // 133
  set({ syncing: true })                              // 134
  try {
    const snap = await api.fetchAll()                 // 136
    ...

```
全文件搜 `syncing`（store.ts:104/133/134/150 加 signOut:192 里那次 set 并不含 syncing）只有 134 置 true、150 置 false 两处，没有任何超时/兜底把它放开。134 与 try 之间没有可抛异常的语句，所以「置了 true 却没进 try」这条常见的假路径不成立——唯一让 syncing 永久为 true 的方式就是 fetchAll 的 promise 永不 settle。

严重度我从「高」降到「中」：本地记账不受影响（addTx/editTx/removeTx 在 195-250 行都不看 syncing，照常直接写云端），云端数据不会丢，App 重开即恢复。真实损失是「这台手机静默停在旧数据上」——用户在另一台设备记的账拉不回来，可能把同一笔重记一遍，属于对账正确性问题而非丢数据。加上 iOS 本来就常把后台 PWA 杀掉重启，实际触发频率不高。

唯一没法在代码里证实的是「iOS 冻结页面时请求真的永不 settle」这一前提——这属于运行时环境行为，我无法在本仓库内证明或证伪。但即便退一步，只要请求长时间不落地（弱网 + 自动重试退避），锁就长时间不放，同样是「切回前台不同步且无提示」，机制本身成立。

- 现象：统计页把分类占比切到「收入」，圆环中心显示的是本月收入，但顶部展开月份选择器后，12 个格子里的数字和上方的「全年支出」仍然是支出金额，而格子里的数字没有任何标签。正在看收入的用户很容易把格子里的数字读成当月收入，据此挑月份，点进去发现对不上。
- 根因：MonthPicker 只读 totals.get(ym)?.expense，Stats 传进去的 monthTotals 其实收入支出都有，但组件没有切换口径的入口，也没有区分当前统计页处在哪个模式。
- 改法：给 MonthPicker 加一个 metric?: 'expense' | 'income' 属性（默认 expense），格子和年合计都按它取值，年合计文案随之改成「全年收入/全年支出」；Stats.tsx 第 241 行传 metric={kind}。流水页保持默认不用改。

### [低] `src/lib/store.ts:290` 新建分类后 10 秒内再改它（换图标/改名），刚建的那条会被同步冲掉一次
- 频率：几年后
- 现象：在记账页用「＋ 新增」建了个二级分类，马上又去分类管理页给它换个图标；如果这几秒里正好有一次同步（切回前台会触发）在路上，同步落地后这个新分类会从列表里消失，记账页里刚选中的它也会自动跳回别的分类，要等下一次同步才重新出现。用户会以为分类没建成功，于是再建一遍。
- 根因：addCategory 给新分类登记了 10 秒的在途保护（pendingCat + setTimeout 删除），但 updateCategory 的 finally 里无条件 pendingCat.delete(id)，会把这条还没到期的保护一并撤掉；此时早于插入发出的那次 fetchAll 返回的快照里还没有这行，applyPending 没有补丁可叠，行就被冲掉了。
- 改法：让两处的生命周期不互相踩：给 pendingCat 的值带上到期时间（Map<string, {row, until}>），updateCategory 的 finally 只在自己是最后一个写入者且已过 addCategory 的保护期时才删；最简单的做法是 updateCategory 结束时不直接 delete，而是 setTimeout(() => pendingCat.delete(id), 10_000)，与新增保持同一套窗口。改完按项目纪律在 store.test.ts 里补一例（先把修复改回旧写法确认会红）。

### 预算与自动化

#### 月度总预算 + 分类预算 + 超支提醒（中等）

- **值不值得做**：五个里唯一每天都会看的。用户现在首页能看到「本月花了 1840」，但看不到「还能花多少」。统计页的饼图是回顾，预算是前瞻。已经在用 5 大类且 note 里写清了口径（日常餐饮=校园吃饭、经常生活开支=通勤水电房租），说明他心里已经有分类预算的概念，只是 App 没接住。落到现象：首页多一条进度条「本月 3000，已花 1840，剩 1160，还有 12 天，日均可花 96」，某大类超了那一行变红。注意「提醒」在没有推送的前提下只能是「打开 App 时看到」，不是「花超了手机震一下」，这点要先跟用户对齐，否则他会觉得功能没做完。
- **涉及文件**：supabase/migrations/0004_app_settings.sql, src/types.ts, src/lib/api.ts, src/lib/store.ts, src/lib/compute.ts, src/lib/compute.test.ts, src/lib/csv.ts, src/pages/Home.tsx, src/pages/Stats.tsx, src/pages/Budget.tsx, src/App.tsx, src/pages/Settings.tsx
- **框架挡路的地方**：① Snapshot 三张表是硬编码的，加第 4 张要同时改 7 处：types.ts 的 Snapshot、api.fetchAll、api.importAll、store.ts 的 Cache/readCache/writeCache/signOut、csv.ts 的 ExportFile/buildJson/parseImport、store.test.ts 的 snap() 辅助函数。漏改 readCache 的现象：老用户本机 jz_cache_v1 里没有 budgets 字段，budgets.map() 抛错，首页被 ErrorBoundary 换成错误页。② csv.ts 的 parseImport 硬校验 obj.version !== 1 就抛「不是本应用导出的 JSON 文件」；升到 version 2 后，用户手上已导出的 v1 备份会被拒绝恢复 —— 这是「明年想恢复今年备份，发现恢复不了」的坑。③ store.ts 的在途补丁只有 pendingTx / pendingCat，改完预算立刻切走再切回，refresh() 的旧值会把它冲掉，用户看到「刚设的 3000 又变回 2000」。④ TabBar.tsx 是 grid grid-cols-5，五格已满，预算页进不了 Tab。
- **实施要点**：表设计建议一步到位做成通用 app_settings(user_id, key text, value jsonb)，预算、储蓄目标、周期规则全塞进去，「加表」这 7 处的成本只付一次。预算行本身：month 为 null = 默认预算（每月生效，用户设一次就不用管），category_id 为 null = 总预算，唯一索引卡住 (user_id, month, category_id)。金额照旧走 api.ts 里现成的 centsToDb/centsFromDb，不新写转换。预算只挂一级分类：byCategory() 已经按一级聚合可以直接复用，而且挂二级会跟 Categories.tsx 的「移动二级到其他大类」打架 —— 用户 09-04 刚把「通勤交通」移到「日常餐饮」下，那种移动会让二级预算的归属突变。纯函数 budgetProgress(txs, cats, budgets, ym, ref = today()) 必须把 ref 做成参数，否则「本月已过 X 天」没法测；dailyCumulative 就是这个 pattern，照抄。修 parseImport 时改成 version >= 1、缺失字段兜底 []，别改成只认 2。跟三条铁律不冲突：预算只看 expense，transfer/adjust 天然不进。

#### 周期性账单（房租/订阅）—— 建议只做「到期提醒 + 一键预填」，不做自动生成（困难）

- **值不值得做**：价值中等。用户有「经常生活开支/房租、水电燃气、话费网费」，一个月也就 2–4 笔，省下的手工操作有限；真正值钱的是「不漏记」—— 忘了记房租那 2000，要等月末余额校准才发现对不上。但「自动生成」这条路在本项目里有真实缺陷，见 blockers；换成「提醒+预填」代价只是每月多点两下，风险从高降到接近零。
- **涉及文件**：supabase/migrations/0004_app_settings.sql, src/types.ts, src/lib/api.ts, src/lib/store.ts, src/lib/date.ts, src/lib/recurring.ts, src/lib/recurring.test.ts, src/pages/Entry.tsx, src/pages/Home.tsx, src/pages/Recurring.tsx, src/App.tsx, src/pages/Settings.tsx
- **框架挡路的地方**：自动生成这条路的四个硬伤（这就是「计划本身的缺陷」）：① 没有服务端，只能在 App 被打开时补算。补出来的记录日期必须写「应发生那天」而不是 today()，否则 8 月房租 9 月 3 号补上会记进 9 月，byCategory('2026-08') 少 2000 而余额又是对的，用户看到「8 月支出凭空少了一笔」。② 用户手机和电脑两端都用，visibilitychange 会让两边同时 refresh、同时判定「9 月房租还没生成」、各插一条 —— transactions 表里没有任何约束能挡住。前端判重挡不住，必须在库里加 recurring_id + due_date 列和 unique index (user_id, recurring_id, due_date) where recurring_id is not null，靠 23505 兜底。③ store.addTx 的失败路径一定 showToast(`保存失败：…`)，而 api.friendlyError 把 23505 一律翻成「已有同名分类」；后台生成撞重复时，用户会看到一句跟场景完全无关的红字。④ 自动生成的支出立刻改变账户余额，但钱可能还没真扣；用户下次余额校准会写一条 +2000 的 adjust，统计页「累计未记录差额」变正数，而 README 说正数=有收入没记 —— 口径直接说反。
- **实施要点**：推荐落地形态：recurring_rules 存规则 + last_done_date；首页一条横幅「房租该交了（每月 1 号）」，点一下跳 /add?tpl=<ruleId>，Entry.tsx 预填金额/分类/账户/日期，用户按一下保存键。重复插入在人工确认下不可能发生，日期用户可改，余额永远反映真实。前置改造：date.ts 缺「按月加减具体日期」—— 现在只有 addDays(ymd,n) 和 shiftMonth(ym,n)（后者只吃 YYYY-MM），「每月 31 号」的账单在 2 月要钳到 28/29 号，得新增 addMonths(ymd, n) 并补测试，这是纯函数层实打实的空缺。若用户坚持要自动生成，最低限度必须先做两件事：给 store 的三个写动作加 { silent?: boolean } 走静默路径，以及上面那条唯一索引。

#### 记账提醒（每天固定时间推送）（困难）

- **值不值得做**：价值中等偏低，而成本是五个里最高的。用户已经在天天记（09-03、09-04 连续有账），定时提醒解决不了真正的漏记场景 —— 「出门在外当场没记」。而且 iOS PWA 的推送到货率本来就不稳，用户很可能得到「有时候推、有时候不推」的体验，比没有更糟。强烈建议先用替代方案顶，见 notes。
- **涉及文件**：vite.config.ts, src/sw-entry.ts, src/App.tsx, src/pages/Settings.tsx, src/lib/push.ts, supabase/migrations/0004_push_subscriptions.sql, supabase/functions/daily-remind/index.ts
- **框架挡路的地方**：① vite.config.ts 用的是 generateSW（VitePWA 只给了 registerType + workbox，没有 strategies: 'injectManifest'、没有 srcDir/filename），Workbox 自动生成 SW，项目里根本没有自己的 SW 源文件 —— 而 Web Push 必须在 SW 里监听 push 和 notificationclick，现在无处可写。要切 injectManifest 并手工重现 precache + 等待激活行为，而 App.tsx 的 UpdateBanner 和 README 坑 #5/#7 全建在这条链路上，改坏了的现象是「用户永远卡在旧版本」或「一打开白屏」。这是全项目风险最高的一处改动。② 没有服务器发推送：要新增 push_subscriptions 表（带 RLS）+ Supabase Edge Function（Deno + web-push + VAPID 密钥）+ pg_cron 定时，整套后端，跟 README「靠 RLS 保证安全，不用自己写后端」的选型理由正面冲突。③ iOS 三重限制：只有「加到主屏」的 PWA 能收（16.4+），Safari 里点「开启提醒」是白点；README 坑 #8 的主屏/Safari 存储隔离对订阅同样成立；用户删掉主屏图标再加回来订阅失效且无任何提示，他只会觉得「提醒坏了」。④ 免费项目 7 天无访问休眠（README #13），休眠期间 cron 不跑，提醒静默消失。
- **实施要点**：两个替代方案，加起来能拿到 90% 的效果、0 风险：(a) 让用户在 iPhone 的「快捷指令 → 自动化」里设一条「每天 21:00 打开 记账」，零代码零维护，这是我建议先给他的；(b) App 内补记提醒 —— 打开时若今天 0 笔就在首页顶一条横幅「今天还没记账」，Home.tsx 里 dayStat.count 已经算好了，只是一个条件渲染，半小时的事。真要上推送，务必先在手机上把「有新版本 → 点更新 → 版本号真的变了」跑通并留作回归基线，再动 vite.config.ts。另外 cron 每天跑一次是否算「访问」从而顺带解决休眠，这是推测，必须实测，别当已知事实写进方案。

#### 常用记账模板 / 一键重复上一笔（容易）

- **值不值得做**：五个里性价比最高的。用户有 5 大类 + 24 个二级，「日常餐饮/午餐/微信」这种组合一天来两次。Entry.tsx 已经用 jz_entry_memory_v1 记住了上次的类型/账户/大类/二级，所以现在是「输金额 → 保存」两步；模板能压到「点一下 → 保存」一步。落到现象：记账页金额上方多一排「午餐 ¥15 · 微信」「咖啡 ¥18 · 支付宝」，点一下全部填好；首页最近流水每行右边多一个「再记一笔」。
- **涉及文件**：src/lib/compute.ts, src/lib/compute.test.ts, src/pages/Entry.tsx, src/pages/Home.tsx
- **框架挡路的地方**：① Entry.tsx 第 111–128 行有四个「值为空就填第一个」的 useEffect，其中第 122–128 行那个会检查「childId 不在 children 里就换成 children[0]」。如果模板是 mount 之后用 setState 填的，这几个 effect 会在同一轮里把分类改回「最近用过的那个」。现象：点「午餐 ¥15」模板，金额对了但分类跳回「早餐」。必须在 useState 的初始值里就把模板读进去，跟现在读 memRef.current 一样，不能走 effect —— 这是唯一一个真会咬人的地方。② 不能复用 ?id= 那条路做「复制」：save() 里 id: editing?.id ?? newId()、created_at: editing?.created_at ?? nowIso()，只要 editing 非 null 就走 editTx 覆盖原记录。现象：用户以为复制了一笔，其实把上个月那笔改成了今天的。复制模式必须让 editing 保持 null，只借字段做初始值，用 ?copy= 而不是 ?id=。③ 模板预填金额后，nextAmount() 的逻辑是「int === '0' 才替换」，预填 "15" 再按 8 会变成 "158" 而不是 "8"，用户会觉得键盘坏了；要加一个 amountPrefilled 标志，第一次按数字键先清空。
- **实施要点**：关键结论：不需要建表，也不该建。模板可以从历史流水现算 —— 在 compute.ts 加纯函数 frequentCombos(txs, ref = today(), days = 60, n = 4)，统计近 60 天 (category_id, account_id, amount) 三元组的出现次数取前 4。零 migration、零跨设备同步问题、零「模板管理」界面，模板还会自动跟着习惯变。这跟 compute.ts 里已有的 recentChildOrder（从流水反推偏好）是同一个 pattern，风格一致。「重复上一笔」= sortTxs(txs)[0] 做初始值。这个功能建议第一个做：不动数据库、不动 store、不动分层，纯函数加测试 + 一个页面的初始值，改坏了 git revert 一条 commit 就干净了。

#### 目标储蓄（攒钱目标进度）（中等）

- **值不值得做**：五个里价值最低，建议不单独做。这个模型里「没有初始余额字段」，账户余额 = Σ收入−Σ支出+Σ转入−Σ转出+Σ校准，所以「攒了多少」在数据上就等于「总余额」—— 而总余额已经在首页账户卡、账户页大字、统计页余额曲线各显示过一遍了。做成「目标 5000，当前 3200，64%」只是给同一个数字换个包装，用户看到的是第四遍。真正有增量的是「专款专用」（旅行基金存了 1200），但那需要给流水打标签，扩散面比预算还大。
- **涉及文件**：supabase/migrations/0004_app_settings.sql, src/types.ts, src/lib/api.ts, src/lib/store.ts, src/lib/compute.ts, src/pages/Home.tsx, src/pages/Settings.tsx
- **框架挡路的地方**：① 没有承载「这笔钱是为某个目标存的」的地方。要么给 transaction 加 tag 字段（新 migration + 可能要碰 0002 的 tx_shape 约束 + csv.ts 的导出列和表头 + Entry.tsx 的 UI + Ledger.tsx 的筛选），要么只能拿总余额当进度，而总余额本来就到处都有。② 如果只是存一个目标数字，照样撞上跟预算一样的「Snapshot 三张表硬编码、加表要改 7 处」问题 —— 为了一个数字付这个成本不划算。③ 账户只有固定四个（中国银行/招商/支付宝/微信），没有「新增账户」的入口（api.ts 只有 updateAccount，没有 addAccount），所以「开一个储蓄账户」这条路目前也走不通，得先补 addAccount。
- **实施要点**：如果用户主动提，先用现有功能顶，零代码：设置页把某个账户改名叫「攒钱」（updateAccount 已支持改名），往里转账，账户页那一行的余额就是进度 —— 转账天然不进收支统计，完全符合铁律。真要做，务必和预算共用同一张 app_settings 表，别为它单开一张；进度值直接复用 compute.ts 现成的 balances() / totalOf()，不要新写口径，否则会出现「首页说 3200、目标卡说 3180」这种自相矛盾。

5) SVG 的 `<text>` 不会自动折行，中文换行和分类名截断要自己算宽度。
- **实施要点**：推荐做法是在 `src/lib/report.ts` 里手写 SVG（快照 + 月份 → SVG 字符串），这样它是纯函数、能在 node 环境单测、完全不碰 `components/Chart.tsx`，符合现有分层。渲染成 PNG 的那十几行（Image + canvas + toBlob）放在页面侧。

**真正该优先做的是 README「还没做的」里那条自动备份**（GitHub Actions 每天拉全量写进私有仓库）——成本比月报低、解决的是数据会丢这个真问题。月报图片可以当它的附赠品：同一个 report.ts 顺手生成一张。

另外要提醒：统计页现在已经有月份选择器 + 饼图下钻 + 趋势图 + 未记录差额，信息量并不比一张月报图少。所以这个功能的卖点只有「能存下来、能发出去」，把预期定在这里。

#### 真正的离线记账（本地补传队列 outbox）（中等）

- **值不值得做**：有用，而且是这五项里唯一「不看数据量、随时可能咬人」的。现在 src/pages/Entry.tsx 第 178–181 行写死了 `if (!online) { showToast('当前离线，暂不能记账'); return }`，地铁/电梯/出国漫游时直接记不了；更常见的是 README 第 13 条那个坑——免费项目 7 天没人访问会休眠，唤醒前所有写入都失败，用户会看到「保存失败：网络不通」，那笔就丢了。
- **涉及文件**：src/lib/outbox.ts（新建，约 80 行）, src/lib/outbox.test.ts（新建）, src/lib/store.ts, src/lib/api.ts, src/lib/pending.ts, src/pages/Entry.tsx, src/pages/Settings.tsx, src/App.tsx, src/lib/hooks.ts
- **框架挡路的地方**：三个真挡路的地方。(1) src/lib/api.ts 的 addCategory 靠数据库生成 id（`.insert(input).select().single()` 拿返回值），而 Entry.tsx 允许「记账时顺手新建二级分类」——离线时这条路直接断，必须先改成客户端 newId() 生成 id 再 insert。(2) store.ts 的 addTx/editTx/removeTx 的 catch 分支不区分「网线断了」和「服务端说这数据不合法」，两种都走回滚 + 弹「保存失败」。要排队就必须先能区分，否则一条被 CHECK 约束拒绝的脏数据会永远卡在队列里反复重试。api.ts 只有 friendlyError 做正则匹配，没有可靠的 isNetworkError。(3) pendingTx / pendingCat 是 store.ts 第 86–87 行的内存 Map，`finally` 里就删掉，关掉 App 就没了；outbox 必须落盘，等于要写一个「持久版的 pendingTx」。
- **实施要点**：分层在这里是实打实帮忙的：src/lib/pending.ts 的 applyPending() 已经是「服务端快照 + 在途补丁 = 该显示什么」的正确合并原语，outbox 只是把这个 Map 落盘并且不在 finally 里清掉，refresh() 第 138–142 行的叠加代码一行都不用改。另外两个关键前提这个项目已经天然满足，很少见：流水的 id 是 src/lib/id.ts 的 newId() 客户端生成，created_at 是 Entry.tsx 第 192 行的 nowIso() 客户端生成——所以离线记的那笔补传时不会变 id、不会跳位置，不需要任何服务端协调。实施顺序建议：先做 api.ts 的错误分类（见 framework_limits 第 5 条），再做 addCategory 客户端 id，最后才是 outbox 本体。用户会看到的现象变化：断网时照样能记，首页顶上多一行「3 笔待上传」，来网了自动补传并消失。别忘了撤销（Entry.tsx 第 223 行那个 undo toast）在离线时是「入队一条 insert 再入队一条 delete」，队列必须能把这对儿抵消掉，否则补传时会先建再删，白跑一趟。触发信号：一个月里出现 ≥2 次「当前离线，暂不能记账」或「保存失败：网络不通」，就该做了。

#### localStorage 换 IndexedDB（容易）

- **值不值得做**：有用，但还很远。缓存里一条流水的 JSON 约 281 个字符（UUID 占大头），localStorage 按 UTF-16 算是 562 字节，5 MiB 上限对应约 9,300 条。按每天 5 笔算 5.1 年、每天 3 笔算 8.5 年才撑满。用户现在只有几十到一两百条。
- **涉及文件**：src/lib/cache.ts（新建，读写抽象层）, src/lib/idb.ts（新建，约 60 行原生 IndexedDB，不装库）, src/lib/store.ts, src/lib/store.test.ts, package.json（可能加 fake-indexeddb devDep）
- **框架挡路的地方**：两个。(1) 现在 store.ts 的 init()（第 111–120 行）里 readCache() 是同步的，冷启动第一帧就有数据；IndexedDB 全异步，中间会闪一帧空状态——用户会看到「本月没有记录」闪一下再变出数字，这是唯一肉眼可见的倒退。解法是保留 localStorage 存「最近 3 个月」的小热片给首帧，IDB 存全量。(2) src/lib/store.test.ts 第 31 行手搓了 FakeStorage 来测 22 项行为，其中 6 项直接依赖 localStorage 的同步语义（去抖只落一次盘、写满降级、退出登录取消在途写入）。store.ts 现在是直接调 localStorage 全局对象，不是可注入的。必须先抽出 src/lib/cache.ts（read/write/clear 三个函数的接口），让测试 vi.mock 掉它，否则要么引入 fake-indexeddb，要么这 6 项测试作废。
- **实施要点**：这一项是分层收益最干净的一项：全项目除了 store.ts 自己，没有任何页面读账本缓存（grep localStorage 只命中 hooks.ts 里存 UI 偏好的 usePersistedState/loadLocal 和 store.ts 自己）。所以换存储引擎真的只动 store.ts 的 readCache/writeCache/persist/signOut 四个地方，7 个页面一行不改。量化触发点：设置页已经显示缓存占用（store.ts 第 40 行 CACHE_LIMIT_BYTES = 5 MiB），并且写满时会弹一次「本机缓存已满，离线时看到的可能是旧数据」——这句 toast 出现就是该动手的信号，不用提前做。顺带说清楚：性能不是这里的瓶颈，实测 10,000 条时 JSON.stringify 只要 9.4 ms（且有 500 ms 去抖，不在按保存的关键路径上），是 5 MiB 容量先到，不是慢先到。

#### 增量同步（只拉变化的行）（困难）

- **值不值得做**：有用，但真正会先咬人的不是流量而是往返次数。src/lib/api.ts 第 66 行 PAGE = 1000，fetchAll 是个串行 for 循环，每次同步要发 2 + ceil(N/1000) 个请求；而 src/App.tsx 第 51–57 行是「每次切回 App 都 refresh 一次」。现在几百条 = 1 个来回无感；3,000 条 = 3 个来回；10,000 条 = 10 个串行来回，到新加坡机房单程 80–200 ms，实测体感 2–5 秒，首页右上角那个「同步中…」会一直挂着。流量反而不紧张：10,000 条一次全量约 2.7 MB 未压缩、压缩后约 450 KB，每天切 30 次约 400 MB/月，离免费版 5 GB/月还远。
- **涉及文件**：supabase/migrations/0004_sync.sql（新建）, src/lib/api.ts, src/lib/store.ts, src/types.ts, src/lib/csv.ts, src/lib/cache.ts, src/lib/store.test.ts, src/lib/compute.test.ts
- **框架挡路的地方**：最大的一条：三张表全是硬删除（api.ts 第 97–100 行 deleteTx 直接 `.delete()`），没有任何删除痕迹。手机上删一笔，电脑那边用 `where updated_at > 游标` 永远拉不到这个消息，那笔会在电脑上诈尸——这是增量同步最典型的翻车方式，而且用户会以为是「数据错乱」。必须新增 0004 迁移建 deletions(user_id, table_name, row_id, deleted_at) 表 + 删除触发器（比给 transactions 加 deleted_at 软删除便宜得多，软删除会牵连 compute.ts 里每一个 filter）。同一个迁移里顺手加 `create index on transactions (user_id, updated_at)`。第二条：updated_at 用的是 now()（事务开始时间），同一毫秒的两条会互相遮挡，游标必须用 `>=` 加客户端按 id 去重，不能用 `>`。第三条：types.ts 的 Transaction 加 updated_at 会传染到 csv.ts 的 ExportFile（version 1 要升 2）——不过 parseImport 第 66 行已经在 strip updated_at 了，作者当时就预留了，改动比想象小。
- **实施要点**：服务端其实已经准备好一半了：0001_init.sql 三张表都有 updated_at 和 set_updated_at 触发器，只是 api.ts 的 TX_COLS（第 19 行）根本没 select 它。真正缺的是删除墓碑——见 blockers。分层在这里帮了一半：refresh() 从「整份替换」改成「按 id 合并」，applyPending 已经是现成的合并原语，页面拿到的还是完整的 transactions 数组，7 个页面一行不改。但有个假抽象要留神：refresh() 第 143 行 `set({...merged, ...})` 每次都产出新数组，哪怕这次一行都没变——App.tsx 每次切回前台都触发，于是所有页面的 useMemo 全部作废重算一遍（实测 30,000 条时 sortTxs 10 ms + balanceSeries 5.5 ms + monthTotals 2.5 ms，手机上乘 2–3 倍，合起来约 50–70 ms 的白干）。做增量同步时必须顺手补上「没变化就保留旧数组引用」。量化触发点：流水 > 5,000 条，或者 Supabase 控制台的 Egress 月用量 > 2 GB。但在那之前先做「便宜替身」（见下一条），能把触发点从 5,000 条推到 25,000 条以上，多买好几年。

#### 【前置·便宜】fetchAll 分页尺寸 + refresh 无变化不换数组引用（容易）

- **值不值得做**：这是上一条的「穷人版」，两处改动加起来不到 20 行，没有数据库改动、没有新概念，却能把增量同步的必要性推迟好几年。后台 max_rows 已经调到 20000（README 坑 1），但 api.ts 第 66 行还写着 PAGE = 1000，往返次数白白多了 5 倍。
- **涉及文件**：src/lib/api.ts, src/lib/store.ts, src/lib/store.test.ts
- **框架挡路的地方**：无。PAGE 提到 5000 的唯一风险是单次响应变大（5000 条约 1.35 MB 未压缩），移动网络下一次超时会重试整页而不是 1/5 页；建议配合把 for 循环加个「第一页不满 PAGE 就直接返回」的短路（现在已经有 `if (data.length < PAGE) break`，所以本来就是安全的）。
- **实施要点**：两件事：(1) api.ts 第 66 行 `const PAGE = 1000` 改成 5000——往返次数从 ceil(N/1000) 变成 ceil(N/5000)，10,000 条时从 10 个串行来回降到 2 个，同步耗时直接砍掉七八成。(2) store.ts refresh() 第 143 行落地前先比一下「条数 + 每条 id 是否一致」，一样就只 `set({ lastSync, syncFailed:false })`，不动 transactions 数组。第二条要配一个新测试（store.test.ts 里加：连续两次 refresh 拿到同样的快照，第二次不能让数组引用变化），并且按 CLAUDE.md 的纪律先把改动改回旧写法确认它会变红。用户会看到的现象：切回 App 时「同步中…」一闪而过，页面不再有那下轻微的卡顿。这条应该现在就做，不用等任何触发信号。

#### 首屏与包体优化（ECharts 占多大）（中等）

- **值不值得做**：实测数字：首屏主包 index-*.js 587 KB 原始 / 170 KB gzip，图表包 Chart-*.js 553 KB 原始 / 185 KB gzip，CSS 21 KB / 5 KB。主包拆开是 react-dom+scheduler 56 KB gzip、react-router 30 KB、@supabase 52 KB、react+zustand 5 KB、应用自己的代码只有 27.5 KB。也就是说 ECharts 一个包比整个应用主包还大，而应用自己写的代码只占全部下载量的 7%。
- **涉及文件**：vite.config.ts, src/components/Chart.tsx, src/lib/supabase.ts, src/lib/api.ts, package.json
- **框架挡路的地方**：一个被文档掩盖的事实：Chart.tsx 第 1 行注释和 README 都说「统计页 React.lazy 拆包，首屏不背这个包」——代码确实拆了（Home.tsx 第 11 行、Stats.tsx 第 14 行都是 lazy），但 vite.config.ts 第 41 行的 workbox.globPatterns 是 `**/*.js`，dist/sw.js 里 precacheAndRoute 明明白白列着 assets/Chart-*.js。结果是：Service Worker 在首次安装时照样把 553 KB 全下下来，而且每次发版（文件 hash 变了）整包重下一遍。所以「首屏不背这个包」只在「不阻塞第一次绘制」这个意义上成立，网络上一个字节都没省。
- **实施要点**：按性价比排：(1) 最便宜、零风险：vite.config.ts 里把 Chart 块从 globPatterns 里排除，改用一条同源的 CacheFirst runtimeCaching 规则。首装下载从约 360 KB gzip 降到 175 KB，图表包等用户第一次点「统计」时才拉、拉完就缓存。只动一个文件。注意第 45 行现在写死 `runtimeCaching: []` 并注释「不缓存任何跨域请求」——加同源规则不违背这个意图，但要把注释改掉，别让下一个人误会。(2) 中等收益：@supabase 的 52 KB gzip 里，realtime-js（实时订阅）、functions-js（边缘函数）、storage-js（文件存储）、auth-js 的 webauthn 全都打进去了，实测在打包产物里都能 grep 到，而这个应用一个都没用——supabase-js 的 createClient 会 eager 构造 RealtimeClient，摇树摇不掉。改成直接依赖 @supabase/postgrest-js + @supabase/auth-js，能省 25–35 KB gzip，而且改动完全落在 supabase.ts + api.ts 这两个文件里——这正是分层设计要保护的场景，收益兑现得很干净。(3) 大头但最贵：ECharts 185 KB gzip 只画了 1 个环形图 + 2 条折线。已经是 echarts/core 按需引入的最小集了，再瘦只能自己用 SVG 画（环形图就是几行 path 数学，折线图麻烦在 tooltip 和 Chart.tsx 第 42–51 行那个 convertFromPixel 点轴交互）。除非用户明确抱怨「点统计要等」，否则不值得。触发信号：与数据量无关，看用户是否说「每次更新完第一次打开很慢」；4G 上首装 360 KB gzip 大约 2–4 秒。

#### 换掉 Supabase 的成本（中等）

- **值不值得做**：README 写「api.ts 是唯一接触 Supabase 的文件，换后端只改这里」。这话对了一半：管道确实只在 api.ts（169 行），但规则不在。真正决定成本的是「换到什么」。
- **涉及文件**：src/lib/api.ts, src/lib/supabase.ts, src/lib/money.ts, src/lib/validate.ts（新建）, src/pages/Login.tsx, src/pages/Settings.tsx, src/lib/store.ts, supabase/migrations/*.sql
- **框架挡路的地方**：四个漏点，按会咬人的程度排。(1) 业务规则住在数据库里，不在 TypeScript 里：0001_init.sql 有 4 个触发器/约束——tx_shape（四种类型各自的字段形状、金额 > 0）、categories_depth_guard（最多两级、父子 kind 一致）、tx_category_kind_guard（分类类型必须匹配流水类型）、外加 3 个唯一索引和 RLS。前端 Entry.tsx 的 validate() 只覆盖其中一部分。换到没有触发器的后端（Firebase、D1+Workers、自建 Node），这些规则全部凭空消失，而且不会报错，只会慢慢攒出脏数据。(2) friendlyError（api.ts 第 42–54 行）匹配的是 Postgres 方言：SQLSTATE 23505/23514、GoTrue 的英文文案、JWT。换后端后所有中文错误提示会静默退化成英文原文，用户看到的是一串看不懂的话。(3) money.ts 里的 centsFromDb/centsToDb 被 CLAUDE.md 归为「纯函数，不依赖 store/api」，但它俩的正确性依赖「数据库那列是 numeric(12,2)」这个后端事实——换到用整数分存的后端，centsFromDb 的 `Math.round(Number(v)*100)` 会让所有金额差 100 倍，而且全都还是合法数字，最难发现。实测这两个函数只有 api.ts 在用（compute.test.ts 之外），应该搬进 api.ts。(4) 分层已经破了两个小口：src/pages/Login.tsx 第 2 行和 src/pages/Settings.tsx 第 5 行直接 import 了 lib/api，其中 Settings 的 changePassword 是页面直接发的一次真·后端调用，绕过了 store。CLAUDE.md 白纸黑字写「store.ts 是唯一调用 api.ts 的地方」，现实不是。
- **实施要点**：分档报价：换到同族（Neon + PostgREST、自建 Supabase、Nhost）= 容易，改 supabase.ts 的 createClient 和 api.ts 里 4 个 auth 函数，SQL 迁移原样跑，约 1 天。换到非 Postgres = 困难，要重写 api.ts 169 行 + 把 4 条数据库规则复刻成 src/lib/validate.ts + 重写 friendlyError 的分类 + 解决分类 id 生成 + 找一个 RLS 的等价物（现在 user_id 是数据库端 `default auth.uid()` 打的戳，客户端从不发送，csv.ts 第 65 行 parseImport 还专门 strip 掉它，安全模型完全押在服务端），约 3–7 天。有一件事这个项目已经做得非常好、值得点名：csv.ts 的 ExportFile + api.ts 的 importAll 已经是一套完整的 dump/restore（按 500 条分批 upsert、父分类先于子分类），所以换库的数据搬迁成本几乎为零，剩下的全是代码成本。量化触发点：免费版 500 MB 数据库上限按每行含索引约 500 B 算能放约 100 万条，永远到不了；先到的是 5 GB/月出网（约 10 万条 × 每天 30 次同步）和「7 天无访问休眠」。所以真正的触发信号不是数据量，是政策公告——而防身的办法是先把 README「还没做的」里那条自动备份做掉（GitHub Actions 私有仓库每日跑一次导出 JSON），有了每日快照，任何政策变化都从紧急事故降级成一个周末的活。

#### 【前置·推荐】把数据库里的业务规则抽一份到 lib/validate.ts（容易）

- **值不值得做**：这一条本身不是新功能，但它同时是「离线记账」和「换后端」的共同前置，而且现在做最便宜——规则还只有 6 条，写成纯函数不到 60 行。
- **涉及文件**：src/lib/validate.ts（新建）, src/lib/validate.test.ts（新建）, src/lib/store.ts, src/pages/Entry.tsx
- **框架挡路的地方**：无。数据库的触发器和 CHECK 全部保留当最后一道防线，前端这份只是提前拦。唯一要注意的是两边规则会漂移——建议在 validate.ts 顶上贴一段注释，写清「本文件是 supabase/migrations/0001_init.sql 里 tx_shape / categories_depth_guard / tx_category_kind_guard 的 TypeScript 副本，改数据库约束时必须同步改这里」，并在 validate.test.ts 里逐条对着 SQL 写用例。
- **实施要点**：要复刻的是这几条：expense/income 必须有 category_id、不能有 to_account_id、金额 > 0；transfer 必须两个账户且不相同、金额 > 0；adjust 必须有 account_id、不能有 category_id、金额可正可负可为 0；分类最多两级；子分类 kind 必须等于父级；流水的分类 kind 必须等于流水 type。为什么现在做：一旦上了离线队列，离线时没有服务端把关，一条非法数据会先进本地、显示得好好的，几小时后补传时才被数据库拒绝——用户看到的是「我昨天记的那笔今天弹了个保存失败」，而那时候他早忘了当时输了什么。有了 validate.ts，store.addTx 在入队之前就能挡住，用户当场就知道。顺带这也是 Entry.tsx 的 validate() 从「UI 提示」升级成「数据契约」的时机，两者可以合并成一份。

## 四、框架的天花板（会限制未来扩展的架构约束）

### Snapshot 就是硬编码的三张表，加第 4 张表要同时改 7 处：types.ts 的 Snapshot、api.fetchAll、api.importAll、store.ts 的 Cache/readCache/writeCache/signOut、csv.ts 的 ExportFile/buildJson/parseImport、store.test.ts 的 snap()。而且 parseImport 硬校验 version !== 1 就整个拒绝。

- **什么时候成为真问题**：第一次做任何「要存到云端、要在手机和电脑之间同步」的功能就撞上 —— 预算、周期规则、储蓄目标三个全中。只有「模板从历史流水现算」这条路能绕开。
- **对策**：一次性加一张通用 app_settings(user_id, key text, value jsonb, unique(user_id,key))，预算/目标/周期规则全塞进去，这 7 处的改动只付一次。同时把 readCache 的字段校验改成缺失兜底 ?? []（否则老缓存会让首页变成 ErrorBoundary 错误页），把 parseImport 的 version !== 1 改成 version >= 1（否则用户手上的旧备份将来恢复不了）。

### localStorage 全量缓存有硬上限。实测一条流水序列化后 274 个字符，浏览器按 UTF-16 计约 550 字节/条，5 MiB 大约装 9500 条。

- **什么时候成为真问题**：按用户 5 笔/天算约 5.2 年，10 笔/天约 2.6 年。加预算、周期规则这些只多几十行，不影响这个量级 —— 真正推它到顶的只有流水条数本身。
- **对策**：现象不是丢数据：cacheDegraded 会变 true、设置页进度条变红、弹一次「本机缓存已满」，云端数据完好，只是离线打开看到的是旧账本。到时候把 store.ts 的 writeCache 改成只写近两年流水（一行 filter），或换 IndexedDB；改动确实只集中在 store.ts / api.ts，README 的判断是对的。

### 整个应用只在浏览器打开时运行，没有任何「到点自动执行」的地方。App.tsx 里只有 visibilitychange 触发的 refresh 和一个每小时查更新的 setInterval，两者都随页面挂起而停。

- **什么时候成为真问题**：周期账单自动生成、每日记账提醒、超支实时推送 —— 三个候选功能里有两个半直接卡在这。用户 10 天没开 App，任何「应该在第 3 天发生」的事都要等到第 10 天。
- **对策**：能退化成「打开 App 时补算」的就退化，但补出来的记录日期必须写「应发生那天」而不是 today()，否则跨月补记会把上个月的钱记进这个月，统计页凭空少一笔而余额又是对的。真需要定时的只能上 Supabase Edge Function + pg_cron；上之前要先实测免费项目 7 天休眠会不会把 cron 一起停掉（README 坑 #13），这一条目前是推测不是事实。

### PWA 用的是 generateSW（vite.config.ts 里 VitePWA 只给了 registerType 和 workbox，没有 strategies: 'injectManifest'），项目里根本没有自己的 Service Worker 源文件。

- **什么时候成为真问题**：只在做 Web Push 时咬人 —— push 和 notificationclick 两个事件必须写在 SW 里，现在无处可写。除此之外这个配置完全够用。
- **对策**：要切 strategies: 'injectManifest' 并自写 src/sw-entry.ts，同时手工重现现在 registerType: 'prompt' 的等待/激活语义 —— App.tsx 的 UpdateBanner 和 README 坑 #5（横幅点不到）、#7（iOS 主屏 App 不主动查更新）全建在这条链路上。改之前先在手机上把「有新版本 → 点更新 → 版本号真的变了」跑通留作回归基线，别在没有基线的情况下动它。

### 写路径只有一条：乐观更新 + 失败必弹红字。store.ts 的 addTx/editTx/removeTx 每条失败分支都 showToast(`保存失败：…`)，而 api.friendlyError 把数据库 23505 一律翻成「已有同名分类」。

- **什么时候成为真问题**：任何后台或批量写入 —— 周期账单自动生成撞上重复插入、将来的微信/支付宝账单导入、模板批量落库。用户会看到一句跟当前场景毫无关系的红色错误，比不提示更让人困惑。
- **对策**：给三个写动作加可选的 { silent?: boolean }：静默路径只把 syncFailed 置真、不弹 toast，留给页面自己决定怎么展示；同时把 friendlyError 的 23505 分支按表区分文案（分类重名 / 该账单本月已生成 / 记录已存在），别再一句话包打天下。

### TabBar.tsx 是 grid grid-cols-5，五格已满（首页/流水/＋/统计/账户），中间那格是记账按钮。430px 宽下塞第 6 格每格只剩 71px，图标加两个汉字会挤成一团。

- **什么时候成为真问题**：预算功能上马时。预算是唯一「需要每天扫一眼」的新功能，如果只能从设置页两跳进去，等于做了没做 —— 用户不会为了看还剩多少钱点三下。
- **对策**：预算做成 Home.tsx 上的常驻卡片（进度条 + 剩余金额 + 剩余天数），点卡片才进 /budget 详情页，TabBar 一个字不动。要注意 CLAUDE.md 第 11 行写的「需要的话在 components/TabBar.tsx 加一项」这条流程对预算是不成立的，实施前得先知道这个例外，否则会照着规矩去改 TabBar 然后发现塞不下。

### 全量内存模型 + localStorage 全量快照缓存。store.persist() 每次增删改都 JSON.stringify 整份流水写进一个 key（jz_cache_v1），上限写死 CACHE_LIMIT_BYTES = 5 MiB。

- **什么时候成为真问题**：实测当前行形状单条 JSON 278 字符（UTF-16 算 556 字节），5 MiB 约放 9400 条。按每天 5–8 笔算是 3–5 年。但这个天数会被「给 Transaction 加字段」直接缩短：加 tags 降到约 8800 条，加 splits 降到约 6600 条。也就是说每加一个主行字段，就等于提前几个月触顶。
- **对策**：1) 定一条新规矩：能不进 Transaction 主行的数据就别进（这正是选 tags text[] 而不是关联表、选 splits 短键名的理由）。2) 触顶的现象已经被兜住了——store.persist 的 catch 会设 cacheDegraded 并弹一次「本机缓存已满，离线时看到的可能是旧数据」，云端数据不受影响，Settings.tsx 还有进度条能提前看到。3) 真到那天按 README 第八节的计划换 IndexedDB、只加载近两年，改动集中在 store.ts 的 readCache/writeCache 和 api.ts 的 fetchAll，页面一行不用动。

### 每次切回前台都全量重拉整张表。App.tsx 的 visibilitychange 监听 → store.refresh() → api.fetchAll()，按 1000 一页循环拉完全部流水，外加全部账户和分类。没有增量同步。

- **什么时候成为真问题**：几千条时，每次从别的 App 切回来要等一两秒才刷新，且吃掉一次全量流量；一天切十几次就是十几次全量。加了 tags/splits 让每行变大之后同步变慢。到一万条以上（≥11 页）会明显感到「切回来卡一下」。
- **对策**：改增量拉取的条件已经具备：transactions 表有 updated_at 列和 trg_tx_upd 触发器，可以只拉 `updated_at > lastSync`。唯一的坑是删除的行靠增量发现不了，要配一张 tombstone 表或者每天全量一次。改动完全落在 api.ts（新增 fetchSince）和 store.ts（refresh 分两条路），页面和 compute.ts 都不用动。

### Snapshot（accounts / categories / transactions 三个数组）是所有环节的共同单位：store.readCache 的三个 Array.isArray 校验、csv.ts 的 ExportFile（version: 1）、csv.ts 的 parseImport（`obj.version !== 1` 直接抛）、api.importAll 的分批 upsert（还带父分类先于子分类的顺序）。

- **什么时候成为真问题**：任何「加第四张表」的功能都会咬——真正的标签表、拆分明细表、附件表、预算表都是。要同时改这五处，漏一处的现象很难看：漏 readCache 就是冷启动白屏，漏 parseImport 就是「我的备份导不回来了」。
- **对策**：1) 能用「给 transactions 加一列」解决的一律别建表——单人记账全量在内存里筛，关联表买不到任何东西。2) 真要建表时，把 version 提到 2 的同时让 parseImport 同时兼容 1 和 2（现在是严格 !== 1 就抛，改成白名单 [1,2]），否则用户之前导出的所有备份立刻作废。3) 改 Transaction 形状时同步把 CACHE_KEY 从 jz_cache_v1 提到 v2，强制丢弃老缓存——readCache 只校验三个数组存在、不逐字段校验，缺字段的老行会被直接喂给页面。

### 数据形状的真正裁判在数据库，不在 TypeScript：0001_init.sql 的 tx_shape CHECK（expense/income 必须有 category_id、amount > 0、to_account_id 为空）、tx_category_kind_guard 触发器（分类 kind 必须等于流水 type）、categories_depth_guard 触发器（分类最多两级）。

- **什么时候成为真问题**：拆分账目想让主行 category_id 为空、批量清空分类、跨 type 批量改分类、想加第三级分类——四种都会被 Postgres 直接拒绝。而前端只会弹一句 api.friendlyError 把 23514 翻译出来的「数据不合法（类型与字段不匹配）」，用户完全不知道自己踩了什么。
- **对策**：1) 设计新功能时先对着这三条读一遍，看看能不能绕过去（比如拆分保留 category_id 指向最大的一份，约束就一行不用改）。2) 真要改，照 0002_optional_account.sql 的样子来：drop constraint if exists + add constraint 重建，一次迁移；别把约束删光——它是导入脏数据时唯一的拦网。3) 前端在提交前先做同样的校验（Entry.tsx 的 validate() 就是这个位置），把错误话说清楚，而不是让用户去猜那句「数据不合法」。

### 写模型是逐行的，没有批量、没有跨系统事务。store.ts 的 pendingTx 是 Map<id, Transaction>，三个动作都是「乐观改内存 → 发一次单条请求 → 失败按 id 换回旧值」；api.ts 只有 insertTx / updateTx / deleteTx 单条版本。

- **什么时候成为真问题**：批量编辑（循环调 editTx 会变成 N 次往返、失败时改一半）、拆分账目走多行方案（一次要写 N 行且要么全成要么全败）、照片附件（要同时写 DB 行和 Storage 对象，删除时也要成对）。
- **对策**：同库内的批量：新增 editTxMany / removeTxMany，用 .in('id', ids) 一次往返（一个语句就是一个事务，天然全成或全败），并一次性把 N 条补丁塞进 pendingTx、失败时按 id 逐条换回；注意 PostgREST 走 query string，一次别塞超过 200 个 uuid。跨系统（Postgres + Supabase Storage）则根本没有事务可用，只能定顺序（先传文件再写行，删行时容忍孤儿文件）并接受偶发垃圾——这也是我建议不做照片附件的主要理由之一。

### Ledger.tsx 从骨架上就是「按月」的，全项目没有任何跨月流水视图。ym 状态 + MonthPicker + 筛选 useMemo 第一行的 inMonth(t, ym) + monthSummary(txs, ym) + 吸顶栏 --ledger-sticky-h 动态测高 + target 滚动定位 + 从统计页跳转带的 ?ym/?date 参数，六处互相咬合。

- **什么时候成为真问题**：搜索、按标签浏览、跨月的批量操作——三个都需要「不限月份的一列流水」。想在 Ledger 里加一个「跨月模式」开关，这六处逻辑会全部搅在一起，而 Ledger 是已经稳过一轮真机验收的页面。
- **对策**：新建 pages/Search.tsx，按 CLAUDE.md 的「加一页 = 一个文件 + App.tsx 一行」走，Ledger 只加一个入口按钮。可复用的现成件比想象中多：TxRow 的 showDate 属性本来就是为跨月列表准备的（Home.tsx 的「最近流水」在用），compute.ts 的 sortTxs 直接能用，Sheet / DatePicker / ChipGroup 一行不改。另注意列表没有虚拟滚动，跨月结果必须截断渲染（前 200 条 + 提示）。

### 全量数据装内存 + localStorage 全量缓存（`src/lib/store.ts` 的 `jz_cache_v1`）

- **什么时候成为真问题**：实测一条流水的 JSON 是 278 个字符 = 556 字节（localStorage 按 UTF-16 算），5 MiB 上限对应约 9,400 条。纯手动记账一天 3 笔要 8 年才撞线；但只要上线账单导入，一年的微信+支付宝流水就是 1,500~3,000 条，3~5 年必撞。撞线之后用户看到的现象是：设置页缓存条变红、弹一次「本机缓存已满，离线时看到的可能是旧数据」——云端数据不会丢，但离线打开看到的是旧账本。另一个更早出现的现象：`balanceSeries` 每次切换统计页的时间范围都要把全部流水整份复制并排序，几千条起在手机上会有可感知的卡顿。
- **对策**：README 已经指了方向且方向是对的：换 IndexedDB + 只加载近两年，改动集中在 store.ts / api.ts，compute.ts 和所有页面不动。关键是**做账单导入之前先把这件事排进计划**，别等撞线再改——撞线时用户已经有几千条真数据了，迁移风险高得多。

### 一笔流水只有一个 `amount` 字段，转账两边共用它（`compute.ts` 的 `applyTx` + 数据库 `tx_shape` 约束）

- **什么时候成为真问题**：任何「转出金额 ≠ 转入金额」的场景：多币种换汇、跨行转账手续费、信用卡还款的零头、微信提现到银行卡的手续费。现在的模型表达不了，用户能看到的现象是余额对不上，只能再补一条校准把差额抹平——而校准会被统计页当成「未记录差额」，把一个本来能解释的手续费变成一个看起来像漏记的数字。
- **对策**：加 `to_amount` 列并改 tx_shape 约束，`applyTx` 的 transfer 分支两边各用各的数。这和你们已列待办里的「转账两边分别判断」是同一段代码、同一次改动，应该合并做完，别改两遍。

### 「单用户」写死在数据库层：三张表的 RLS 都是 `user_id = (select auth.uid())`，且 user_id 有 `default auth.uid()`；0001 种子脚本还写死取 `auth.users` 里最早的那个用户

- **什么时候成为真问题**：任何形式的共享（家人、对象合账、给会计看），以及任何「第二个账号」的场景——包括你自己想开一个测试账号试新功能。
- **对策**：换成 ledger_id + ledger_members，成员判断走 `security definer` 函数（否则策略里查 ledger_members 会触发 RLS 无限递归，Postgres 直接报错）。但数据库这一半只是成本的一半，客户端那一半见下一条。

### 没有外部业务键，写入通道也只有单条（`api.ts` 只有 insertTx / updateTx / deleteTx）

- **什么时候成为真问题**：账单导入是第一个受害者：同一段账单期导两次就是两份数据，事后连「哪些是重复的」都判断不了，因为 transactions 只有 uuid 主键，没有任何字段记录这条是从哪来的。以后任何自动化写入（定时抓取、Edge Function 代写）同样受限。批量那一侧：`store.addTx` 是逐条 pending 补丁 + persist 去抖，一次写 2000 条会触发 2000 次状态更新。
- **对策**：加 `source` + `external_id` 两列和 `unique(user_id, source, external_id)` 索引；配一个 `api.insertManyTx` + `store.addManyTx` 的批量通道。批量路径不要复用逐条的 pending 补丁机制，单独写、单独测。

### 乐观更新 + 在途补丁的前提是「只有本机在写」（`store.refresh()` 全量替换 + `lib/pending.ts` 只认本机发出的那几笔）

- **什么时候成为真问题**：共享账本、Edge Function 代写、自动备份脚本回写，甚至同一个人同时开着手机和电脑两个窗口连着改。用户看到的现象是：另一端记的账在本机忽隐忽现，或者本机刚改的被另一端的旧数据盖回去。
- **对策**：真要支持多写入者，得上 Supabase Realtime 订阅 + 按 updated_at 合并，并重写 `store.test.ts` 那 22 项基于单写入者时序的用例。在那之前有一条纪律要守住：**凡是新增的写入路径都必须从 store 走，不许绕过去直接调 api**，否则 pending 补丁会漏掉它，就是「刚记的那笔消失了」那个已经修过的 bug 重演。

### 纯前端 + public 仓库 = 没有任何地方能放密钥，也没有可信执行环境

- **什么时候成为真问题**：大模型自然语言解析、汇率定时拉取、邮件找回密码、周期账单提醒、自动备份、任何需要 service_role 的批处理——全部卡在这一条上。前端 bundle 里的东西等同于公开发布（anon key 是公开级别没关系，别的 key 会被拿去刷账单）。
- **对策**：两个出口，各管一摊：Supabase Edge Function（密钥在服务端，前端仍只经 `api.ts` 调 `supabase.functions.invoke`，不破「只有 api.ts 碰 supabase」这条分层）适合 LLM 解析、汇率代理；GitHub Actions + 私有仓库（密钥放 repo secrets）适合定时任务，README「还没做的」里那条自动备份就该走这条。两条都不需要自己运维服务器。

### 「全量流水常驻内存」是所有 7 个页面的硬假设，store 没有查询接口。Home/Ledger/Stats/Entry/Accounts/Categories/Settings 全都写 `useStore((s) => s.transactions)` 拿整个数组，再各自 useMemo 全表扫描（Home 的 sortTxs(txs).slice(0,5)、Ledger 和 Stats 各算一次 monthTotals(txs)、Accounts 的 balances(txs)）。

- **什么时候成为真问题**：两道线，容量先到。localStorage：一条流水 JSON 约 281 字符 × 2 字节 = 562 B，5 MiB 上限对应约 9,300 条（每天 5 笔 = 5.1 年，每天 3 笔 = 8.5 年）。计算：实测 30,000 条时冷启动 JSON.parse 41 ms、sortTxs 10 ms、monthTotals 2.5 ms（桌面 x86，手机约 2–3 倍）；60,000 条时 parse 94 ms、sortTxs 19.5 ms，开始有肉眼可见的卡。
- **对策**：分两步且不要一起做。第一步（现在就能做，风险为零）：把 Home 的 sortTxs 全表排序换成一次线性扫描取前 5，把 monthTotals 的结果提到 store 里算一次给两个页面共用。第二步（等 5 MiB 告警弹出再做）：在 store.ts 里加一层选择器 useTxSlice(startYm, endYm)，页面从「拿全部」改成「拿这段时间」，同时 IndexedDB 只把近两年加载进内存。注意第二步会改 7 个页面的 useMemo 依赖，是这份清单里最伤筋动骨的一次改动，所以能拖就拖，先把第一步和分页尺寸那条便宜的做掉。

### refresh() 每次都替换整个 transactions 数组引用，哪怕服务端一行都没变（store.ts 第 143 行 `set({ ...merged, ... })`），而 App.tsx 第 51–57 行注册的是「每次切回前台就 refresh」。

- **什么时候成为真问题**：每次从别的 App 切回来，所有页面的 useMemo 全部作废重算。实测 30,000 条时一次白干约 18 ms（桌面），手机上 40–70 ms，用户会感觉切回来时页面「顿一下」。3,000 条以内感觉不到，10,000 条开始能察觉。
- **对策**：refresh 落地前先比对「条数 + id 集合」（或者上了增量同步后比对最大 updated_at），一样就只更新 lastSync，不碰 transactions。改动不到 10 行，收益立竿见影。配一个 store.test.ts 用例：连续两次 refresh 拿到相同快照，第二次数组引用必须不变——按 CLAUDE.md 的纪律，先把改动改回旧写法确认它会变红。

### 三张表全是硬删除，没有任何删除墓碑。api.ts 第 97–100 行 deleteTx 直接 `.delete().eq('id', id)`，删掉就什么都不剩。

- **什么时候成为真问题**：做增量同步的第一天就撞上，而且是最难看的那种翻车：手机上删一笔，电脑端用 `where updated_at > 游标` 拉不到这个消息，那笔会在电脑上诈尸，用户以为「数据乱了」。跟数据量无关，只跟「是否开始做增量同步」有关。
- **对策**：新增 supabase/migrations/0004_sync.sql，建 deletions(user_id, table_name, row_id, deleted_at) 表加删除触发器，同一个迁移里补上 `create index on transactions (user_id, updated_at)`。不要选「给 transactions 加 deleted_at 走软删除」这条路——那会牵连 compute.ts 里每一个统计函数的 filter，成本高一个量级，而且很容易漏掉一处就让余额算错。

### 业务规则住在 Postgres 里，不在 TypeScript 里。0001_init.sql 有 tx_shape（CHECK）、categories_depth_guard、tx_category_kind_guard、set_updated_at 四个触发器/约束，加 3 个唯一索引和 RLS；前端 Entry.tsx 的 validate() 只覆盖其中一部分。

- **什么时候成为真问题**：两个场景。做离线记账时：离线没有服务端把关，非法数据先进本地、界面上一切正常，几小时后补传才被拒——用户会看到「我昨天记的那笔今天弹了个保存失败」。换非 Postgres 后端时：这些规则凭空消失且不报错，只会慢慢攒出脏数据（两级以上的分类、支出记到收入分类上、转账两边同一个账户）。
- **对策**：抽 src/lib/validate.ts 纯函数，把 6 条规则复刻一份，store.addTx/editTx 在写之前先跑。数据库约束全部保留当最后防线。文件顶上必须写清「本文件是 0001_init.sql 里 XX 的副本，改数据库约束时同步改这里」，并在 validate.test.ts 里逐条对着 SQL 写用例——否则两边一定会漂移。现在规则只有 6 条，写完不到 60 行，越早做越便宜。

### api.ts 的错误分类是 Postgres/GoTrue 方言，而且被两个页面直接 import，绕过了 store。friendlyError（api.ts 第 42–54 行）匹配 SQLSTATE 23505/23514、'Invalid login credentials'、'JWT' 等英文文案；src/pages/Login.tsx 第 2 行和 src/pages/Settings.tsx 第 5 行直接从 lib/api import——违反了 CLAUDE.md「store.ts 是唯一调用 api.ts 的地方」这条，其中 Settings 的 changePassword 是页面发出的一次真·后端调用。

- **什么时候成为真问题**：做离线队列时立刻咬人：store 的 catch 分支现在无法区分「网线断了，该排队重试」和「服务端说这数据不合法，该回滚并告诉用户」，两种都走同一条回滚路径。一条被 CHECK 拒绝的脏数据入了队会永远重试下去。换后端时也咬人：所有中文提示静默退化成英文原文。
- **对策**：在 api.ts 里加 `classifyError(e): 'network' | 'auth' | 'conflict' | 'invalid' | 'unknown'`，store.ts 只认这五个枚举来决定「排队 / 回滚 / 提示重新登录」，中文文案搬到 store 或一个 lib/messages.ts 里。同时把 Login.tsx 和 Settings.tsx 的直连改成走 store 的动作（store 加 changePassword），把分层补回 CLAUDE.md 说的样子——现在只有两处，补起来是十几行的事，等漏点变多就不是了。

### money.ts 里的 centsFromDb / centsToDb 被 CLAUDE.md 归类为「纯函数，不依赖 store / api」，但它们其实是数据库适配器——正确性依赖「后端那列是 numeric(12,2)、传回来的是 number 或字符串」这个后端事实。实测这两个函数除测试外只有 api.ts 在用（api.ts 第 24、32 行）。

- **什么时候成为真问题**：换到用整数「分」存储的后端时（很多自建方案会这么设计，因为它更正确）。centsFromDb 的 `Math.round(Number(v) * 100)` 会让所有金额变成 100 倍，而且结果全是合法数字、界面不报任何错——用户会看到余额从 3,200 元变成 320,000 元，是这份清单里最难发现的一类 bug。CLAUDE.md 把它列在「纯函数」里，反而会让人放心不去看它。
- **对策**：把 centsFromDb / centsToDb 移进 api.ts（它们的唯一调用方），money.ts 只留 parseYuan / fmtYuan 这两个真正与后端无关的。同步改 CLAUDE.md 第 10 行的纯函数清单，和 compute.test.ts 第 5 行的 import 路径。这是个 20 分钟的改动，但能让「换后端只改 api.ts」这句话第一次真正成立。
