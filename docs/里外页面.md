# 里外页面

> 硬规矩在 `CLAUDE.md`，这里是完整设计、为什么这么定、以及被否决的做法。

外页面（平时用的）显示修饰过的资产账户余额，里页面显示真实余额。用户 2026-09-07 提的需求：
「里页面需要一个很隐秘的打开方式才可以切换，里外页面主要是四个财务账户余额不同，其他的没有区别。」

## 2026-09-27 起的现行模型：里外校准分家

用户 2026-09-27 提的：「修改的余额也有时点标签，时点前的不动，时点之后的才会变动。」

**一句话**：外页面的校准做成和里页面的真实校准一样的东西——一条有日期的记录，从那天起算，以前的不动。

- **外页面那本账** `facade.outerBook(txs, accounts, fadj, mode)` = 真实流水 − 藏掉的（`hidden`）− 非白条账户的真实校准 + 外页面校准记录（`facade_adjusts` 表）。
  外页面所有算钱的地方只吃它；列表吃 `outerList`（账本去掉外页面校准记录）。里页面一切吃原始流水。
- **外页面校准记录**（`FacadeAdjust`：`account_id / date / cents / created_at`）：「从 `date` 起外页面这个账户的余额加 `cents`」。
  它变成一条 `adjust` 流水喂给 `balances` / `balanceSeries`（`facadeAsTx`），所以进余额、进曲线（那天一级台阶），不进收支统计。
- **怎么写**（`Accounts.tsx`）：差额 = 填的「对外显示」− 外页面现在显示的数（`facadeDelta`），记在改的那天。
  外页面点非白条账户的「校准」只写这一条；里页面校准弹层有「实际余额」「对外显示」两个框和一个备注框：
  改实际余额 → 一条真实校准（可带备注），且「对外显示」预填「跟着同幅变」的结果，所以外页面默认跟一条同样差额的记录；
  只改「对外显示」→ 只写外页面校准；都不改 → 什么都不写。白条不参与。
- **分家的含义**：真实校准外页面一律看不见（不列、不算，以前是修饰过的账户看不见、没修饰的看得见）；以后删改真实校准，外页面不跟着变，要外页面变再校准一次外页面。
- **两个岔路口，用户 2026-09-27 定**：① 外页面流水里不出现校准行（真实的、外页面的都不出现），只在里页面校准弹层露最近一条「外页面上次校准 9/27 −¥8,000」；② 时点固定是改的那天，不挑日期。
- **它不解决的**：往后花过头外页面一样会负，两种模型一样。这条规则改的只是「历史动不动」。

**迁移**（老偏移量 → 记录，`migrateFacade` / `scripts/migrate-facade.sql`，只 insert 不改任何现有行）：
修饰过的账户 → 一条记在 `FACADE_EPOCH`（2000-01-01）的记录，`cents` = 偏移量 + 该账户没藏掉的真实校准合计；
没修饰的账户 → 每条没藏掉、不为 0 的真实校准配一条同日期同金额的孪生记录；白条不参与；合计为 0 不写。
这样算出来的曲线和老模型（摘掉校准的真实曲线 + 偏移量 + 校准合计整条平移）逐点相同，`facade.book.test.ts` 拿随机账本对过；
`restore.dbtest.ts` 在真 Postgres 上证明 SQL 和 TS 函数写出的是同一批行。记在 2000-01-01 是因为自定义区间能选到很早，
曲线上每一个点都得含着它才和「整条平移」一样。id 由来源 id 推出（前四位换成 `fa01` / `fa00`），重复跑、老备份合并导入都不翻倍。
`accounts.facade_offset` 留在库里不读、不删：回退旧版本时旧代码照常用它。

**为什么单独一张表**而不是 `transactions` 加一列：回退旧版本时旧代码看不见这张表；加列的话旧代码会把假校准当真校准算进里页面，静默算错。

## 规则原文（2026-09-27 之前的老模型，留作历史；现行规则见上一节和 `CLAUDE.md`）

- **里外页面**：外页面（平时用的）显示的资产账户余额 = 真实余额 + `accounts.facade_offset`（整数「分」，null = 不修饰），里页面显示真实余额。
  **只有余额被修饰**——分类统计、月收支、储蓄率、白条、导入导出全是真的，所以两边的"本月支出"一模一样。白条不参与。
  **唯一的例外是「余额校准」**（2026-09-08 加）：外页面下，**被修饰过的账户**（`facade_offset !== null`）的
  `adjust` 记录整条隐身——不进首页最近流水、不进流水页、不进账户页的「本月 ±」、不进余额曲线。「上次校准」的**时间**照常显示（`lastAdjustAt` 拿原始流水算）：2026-09-16 用户发现，藏掉之后修饰过的账户退回「点此输入实际余额核对」，和没修饰的账户并排一看就知道哪两个动过手脚。只露时间不露金额。已知代价：外页面改偏移量不产生校准记录，这个时间不会刷新。
  不藏就露馅：里页面校准支付宝 +6,391 之后，外页面余额是 0.00，卡片底下却写着「本月 +6,391.00」。
  只藏被修饰的账户，`facade_offset = null` 就是「不修饰」，那种账户一个字都不改。
  代价可控——校准从来不进收支统计（`isFlow`），所以两边任何一个统计数字都不会变，变的只是列表里少一行；
  导出、导入、备份走 store 里的原始数组，不经过 `facade.visibleTxs`。
  **外页面的余额曲线要「摘校准」和「平移量加上校准合计」两件一起做**（`shiftSeries` 的第四个参数）：
  只做前一件今天的数字会掉 6,391，只做后一件校准之前会趴在 −6,391 一整年。两件一起做的结果是
  曲线变平、**而今天那个数一个字不变**，所以这个改法不用动数据库里已经存好的偏移量。
  `facade.test.ts` 有一条「曲线末点 = 账户页显示的那个数」守着这个等式。
  偏移量固定，因此里外同幅波动；界面上填的永远是「外面显示多少」，由 `facade.ts` 的 `offsetFor` 反推偏移量。
  切换 = 长按底部 ＋ 1.5 秒（`facade.HOLD_MS`）；切走 App 满 60 秒（`INNER_TTL_MS`）自动退回外页面。
  里页面的记号是**屏幕最顶上一条 2px 深焦糖细线**（`App.tsx` 的 Root）：每一页都在，外人看了只当是设计。
  别改成只在首页做记号——在统计页长按完还得跑回首页确认，等于没解决问题。切换不弹提示，用户明确不要。
  **`mode` 绝不能写进缓存**——冷启动必须永远是外页面，否则这个开关就白做了（`store.test.ts` 有守）。
  外页面点非白条账户的「校准」改的是偏移量、不写流水；真校准要先进里页面。里页面那屏有两个输入框，
  **有没有那些对账信息就是本人辨认自己在哪一边的记号**，所以别给外页面加任何提示文案。
## 几个决定的理由

**为什么存「偏移量」而不是「写死的对外余额」**：偏移量固定，两边就同幅波动——在外页面记一笔，
外面那个数跟着动，看起来是活的；写死一个数则一个月后还是原样，一眼假。

**为什么记号做在每一页的顶部**，而不是只在首页：在统计页长按完还得跑回首页确认，等于没解决问题。
2px 深焦糖细线外人看了只当是设计。切换不弹提示，用户明确不要。

**为什么外页面点「校准」只改偏移量**：外页面是给别人看的，那里输入的「实际余额」意思是
「外面显示多少」。真校准要先进里页面——里页面那屏有两个输入框，
**有没有那些对账信息就是本人辨认自己在哪一边的记号**，所以别给外页面加任何提示文案。

**为什么外模式要藏掉被修饰账户的「余额校准」**（2026-09-08 加）：里页面校准支付宝 +6,391 之后，
外页面余额是修饰过的 0.00，而这条 +6,391 会同时出现在首页最近流水、流水页、账户页的
「本月 ±」和「上次校准」里——余额 0.00 配一行「本月 +6,391.00」，一眼就露馅。
只藏被修饰的账户：`facade_offset = null` 就是「不修饰」，那种账户一个字都不该改。
这是对「只有余额被修饰、流水全是真的」开的唯一一个口子，代价可控——校准从来不进收支统计，
所以两边任何一个统计数字都不会变，变的只是列表里少一行。

**「外面隐藏」为什么是「整条不算」而不是「只藏一行」**（2026-09-16）：用户要的是给某笔收入打个记号、外页面看不见。第一版做成只藏列表那一行、余额曲线统计照算——当天就发现首页「本月支出 5,000」、流水页顶上「4,700」，同一个数两个值：列表和数字用了两本账，必然对不上。改成一本账：`facade.outerTxs` 是外页面唯一的账本，藏了的记录在外页面根本不存在，所有算钱的函数只准吃它。它不解决「藏起来的钱花掉了外面会见底」——那是另一个问题（见下面「常数偏移的天花板」）。

**常数偏移的天花板**（2026-09-16，三个独立分析一致）：只要「每笔账都真」，外面和真实就只差一个常数；要不为负，这个常数最多等于「下次进账之前真实余额的最低点」。按用户当时的花法（日均 333、中行外显 761）只能藏约 761，不是 20,000。「外面按月自动发一笔虚拟收入」被否：要不见底得每月发 10,000，比藏两万更扎眼，且逐月发散。唯一不留痕的流入是真实的流入——把钱真挪出 App、或建「专款账户」、或外页面干脆不显示存量，是仅有的三条路，由用户自己选。

**曲线为什么要「摘校准」和「平移量加上校准合计」两件一起做**：支付宝真实余额 9/7 之前是 0，
那天校准 +6,391 变成 6,391，偏移量 −6,391。只平移不摘校准 → 9/7 之前显示 −6,391，
趴一整年再弹回 0，一眼就是坏的；摘了校准不补平移量 → 今天显示 −6,391，比上面更糟；
两件一起做 → 0 − 0 + (−6,391 + 6,391) = 0，整条平的，**而今天那个数一个字没变**，
所以不用动数据库里已经存好的偏移量。`facade.test.ts` 有一条「曲线末点 = 账户页显示的那个数」守着这个等式。
