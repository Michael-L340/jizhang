# 数据与迁移

> 规矩在 `CLAUDE.md`，这里是「为什么」和「怎么验出来的」。

## 数据模型

三张表，全部带 `user_id`，RLS `for all to authenticated using/with check (user_id = auth.uid())`。

**accounts** — 中国银行、招商银行、支付宝、微信四个资产账户，加四个白条账户（京东白条、花呗、拼多多、美团月付，`kind = 'credit'`，0004 加的）。没有初始余额字段。白条余额为负表示欠款，总资产 = 资产 − 白条欠款。

**categories** — `parent_id` 为空是一级。触发器限制最多两级、父子 `kind` 必须一致。`note` 存含义说明。支出 5 大类 + 若干二级，收入 6 个单级。

**transactions** — `type` 四种：
- `expense` / `income`：必须有 `category_id`，`account_id` **可为空**（不指定账户，计入收支统计但不影响任何余额）
- `transfer`：必须有 `account_id` 和 `to_account_id` 且不相同
- `adjust`：余额校准，金额可正可负可为 0，必须有 `account_id`

`installments`（0005 加的）：白条分期期数，只对白条账户上的支出有意义，null 按 1 期算。第 k 期在下单月之后第 k 个月到期，每期均分、零头进最后一期。它只用来算「本月应还」和「到第几期」，还款仍是用户记的转账，App 不预排未来的流水。

### 余额公式（`compute.ts`）

```
账户余额 = Σ收入 − Σ支出 + Σ转入 − Σ转出 + Σ校准
总余额   = 四个账户之和
```

两条铁律，所有统计函数的第一行 filter：**`transfer` 和 `adjust` 永远不进收入/支出统计**。转账只是钱在自己账户间挪；校准只修正余额，不制造收支。

### 校准怎么工作

用户在账户页输入"实际余额"，系统算 `差额 = 实际 − 推算`，写一条 `adjust`。差额为 0 也写（金额 0，备注"余额核对"），这样"上次核对时间"能跨设备同步；流水页里 0 元记录显示为灰色。

统计页底部的"未记录差额"= Σadjust，负数说明有支出没记，正数说明有收入没记。这是"一行带符号"写法独有的好处，双边记账给不了。

## 加一列要同时改四处（备份脚本在另一个仓库）

「哪些列要备份」这个约定同时写在三个文件里，其中一个在私有仓库 `Michael-L340/jizhang-backup`：

| 文件 | 里面是什么 |
|---|---|
| `src/lib/api.ts` | `ACC_COLS` / `CAT_COLS` / `TX_COLS` 和 `rowToTx` / `txToRow` |
| `src/lib/csv.ts` + `src/lib/validate.ts` | 导出格式 `ExportFile`、校验规则 `readAccount` / `readCategory` / `readTransaction` |
| `src/lib/restore.dbtest.ts` | 它自己有一份 `select` / `insert` 列清单在模拟备份脚本（2026-09-07 加两列时靠它抓到的） |
| `jizhang-backup/backup.mjs` | `SELECT_ACC` / `SELECT_CAT` / `SELECT_TX` / `SELECT_FA`，**以及** `toAccount` / `toCategory` / `toTransaction` / `toFacadeAdjust`（逐字段构造，SELECT 拉到了这里没写照样丢；2026-09-06 加 `installments` 时真漏过） |

0010（2026-09-27）加的是一张**表** `facade_adjusts`（外页面校准记录，见 `docs/里外页面.md`），比加一列多几处：
`Snapshot` 多一节 `facade_adjusts`（缓存、`signOut`、在途补丁、`restoreSnapshot` 的回滚底稿都带上）、
`wipeAll` 第一句删它（`account_id` 外键 restrict，先删账户会被拒；`step === 'facade_adjusts'` 才是「云端一行没动」）、
`importAll` 在账户之后写它、`backup.mjs` 在账户之前抓它。`cents` 在库里就是整数分（bigint），**不过元↔分换算**，
`toFacadeAdjust` 只保证它是数字。老偏移量由 `scripts/migrate-facade.sql` 一次性换算进来（只 insert，重复跑不翻倍），
`restore.dbtest.ts` 在真 Postgres 上和 `facade.ts` 的 `migrateFacade` 逐行对过。回退到 0010 之前的版本：旧代码看不见这张表，
外页面按留在库里的老偏移量显示，迁移之后新记的外页面校准在旧版本里看不见（升回来就有）。

0011（2026-10-03）又加了一张表 `meter_readings`（电表读数），照 0010 的路数走了一遍：`MR_COLS` / `rowToMr`、
`fetchAll` 分页按 `id` **升序**拉（备份脚本也按 id 升序排，两边导出的 JSON 逐字节一致）、`buildJson` 紧跟在 `facade_adjusts`
后面写（键序和备份脚本一致）、`validate.ts` 的 `readMeterReading`（`centi_kwh` 是不小于 0 的安全整数）、缓存 / `signOut` /
在途补丁（`pendingMr`，删除也登记 `DELETED`）/ 回滚底稿都带上。它和别的表没有外键，`importAll` 排在外页面校准之后；
`wipeAll` 把它排**第一句**，所以 **`step === 'meter_readings'` 才是「云端一行没动」**——上面 0010 那段说的
`'facade_adjusts'` 从此不再是第一句，它失败时电表读数已经删了，要回滚。`centi_kwh` 是整数「0.01 度」（bigint），
和 `cents` 一样不过任何换算。老备份文件没有这一节，按空的收（没有可换算的东西）。CSV 不带它。

还有一处不是列清单但同样会静默出错：`store.ts` 的 `parseCache` 要把新列补成 `null`。
冷启动先用旧版本写的缓存渲染，那份缓存里根本没有这个键，`undefined` 会一路走进算式
（2026-09-07 实测算出 `"2026-09-NaN"`）。

加一列（比如计划中的「微信/支付宝交易单号」）时几处一起改，顺序：先跑 migration → 改 `backup.mjs` → 改 `validate.ts`/`csv.ts`/`api.ts`。**云端迁移和推 `backup.mjs` 要挨着做**：只跑迁移不推脚本，当晚备份会因为「冒出不认识的列」失败；只推脚本不跑迁移，`SELECT` 会报 42703。

**漏改的后果都是静默的**（2026-09-05 在内存版真 Postgres 上逐条实测，不是推测）：

- 只改数据库，没改 `backup.mjs` → 备份文件里根本没有这一列，恢复后**整列是空的，零报错**。现在有第 5 道闸（`assertColumns`）挡着：数据库冒出脚本不认识的列，当晚备份直接失败并发邮件。**这是唯一一道自动防线，别把它删了。**
- 改了 `backup.mjs`，没改 `validate.ts` → 文件里有这一列，但校验器是显式构造对象的，多出来的键在发给数据库之前就被丢掉，同样静默。**这一步没有任何自动防护，只有这条规矩。**
- 曾经以为「列对不上 `parseImport` 会整份拒绝」——**实测不会**。只有「文件里有、数据库里没有」才会报 42703（少跑了一条 migration 才走这条路）。

改完验一遍：让备份跑一次（`gh workflow run backup.yml -R Michael-L340/jizhang-backup`），拿新的 `data/latest.json` 在设置页走一次「整库恢复」，确认新列的值真的回来了。

## 版本回退遇上数据库迁移

2026-09-07 在内存版真 Postgres 上逐条实测，不是推测。

**`git revert` 只回退代码，不回退数据库。** 迁移跑过就在那儿了，回退从来不是对称的。
下面每一条都实测过，别照着直觉改：

| 这次迁移干了什么 | 代码回退到旧版会怎样 |
|---|---|
| **加一个可空列**（0007 就是这种） | ✅ **安全**。旧代码照样跑，新列的值静静躺在库里，代码滚回来它又回来了 |
| 加 `not null` **且有默认值** | ✅ 安全，旧代码 insert 不带这列会走默认值 |
| 把已有的可空列**改成 `not null`** | ❌ 旧代码 insert 不带它 → `23502`，**记账当场失败** |
| **删列 / 改名** | ❌ 旧代码 `select` → `42703`，整个 App 起不来 |
| **改列的类型或口径**（如元→分） | ☠️ **最坏的一种：不报错，静默算错**。实测 `numeric 38.50` 改成 `integer` 后读到 `3850`，旧代码当成 3850 元，差 100 倍 |

「加可空列可以安全回退」有个**前提**：`api.ts` 用的是显式列名常量（`ACC_COLS` / `CAT_COLS` / `TX_COLS`），
旧代码根本看不见新列。**谁哪天图省事改成 `select *`，这条保证就没了。**

还有三条实测出来的连带结论：

- ~~upsert 不带某列时，那列的旧值会保留~~ **这条当年是拿手写 SQL 测的，和 App 真正发的请求不一样**：supabase-js 的 upsert 把每个键都放进 `columns=`，
  PostgREST 对同 id 的行是整行覆盖，校验层又把缺失的列补成 null，所以合并一份旧备份**会**把 hidden / repay_day 这些新列清掉（2026-10-09 审出来的）。
  现在「合并导入」改成只插入云端没有的 id（`ignoreDuplicates`），已有的行一条不动。
- **但「整库恢复」会抹掉**（实测：清空 → 用不含该列的旧文件写回 → 变成 null）。它是先 `wipeAll` 再写入，
  拿加列之前导出的 JSON 恢复，新列就没了。**这跟代码版本无关，跟备份文件的年龄有关。**
- **备份脚本在另一个仓库，`git revert` 碰不到它**，所以回退 App 不会连累每晚的备份。
  反过来，要是回退的是数据库（把列删了），备份会因为 `SELECT` 找不到列而 `42703` 失败并发邮件——是响的，不是静默的。

**所以规矩是**：迁移**只加可空列，永远不删列、不改名、不改类型**。
真要废弃一列，就让它留在库里不管，在 `types.ts` 里加注释说明（`Account.kind` 就是这么处理的）。

## 迁移怎么执行

新增 `supabase/migrations/000N_*.sql`，**不改旧文件**。二选一：Supabase 控制台 SQL Editor 粘贴，
或用 Management API（需要用户临时生成 `sbp_` 令牌，用完删）。令牌走剪贴板，不落盘、不回显。

## 容量：几年后先撞哪一堵墙

按 2026-10-09 的用量（38 天 248 条，每天约 6.5 笔；一条流水的 JSON 平均约 330 字符、最长约 400，当天从备份量的）往后算，数字只是量级：

| 墙 | 上限 | 撞上要多久 | 撞上会怎样 |
|---|---|---|---|
| ~~本机缓存 localStorage~~ | ~~5 MiB（UTF-16，约 660 字节一条，和交易日志共用）~~ | ~~约 3 年~~ | 2026-10-09 已换成 IndexedDB，不再是第一堵墙；IndexedDB 打不开退回 localStorage 时还是这堵 |
| 本机缓存 IndexedDB | 浏览器按设备容量给：iOS 17 起和 Chrome 都是一个站点最多占硬盘的六成（iPhone 上 `estimate()` 报 36～38 GB 左右；iOS 17 之前起步 1 GB） | 几十年 | 写入报配额满 → 设置页标「写不进去」，离线看到旧账本，云端不受影响 |
| 内存里全量账本 | 冷启动 `JSON.parse` 和每次保存的 `JSON.stringify` 都是整本做：桌面实测 6 万条 parse 约 100 ms（手机按 2～3 倍算），stringify 同量级，在 500 ms 去抖之后、不卡按钮 | 6 万条约 25 年 | 变慢，不丢数据；到时候做「只加载近两年」 |
| 每次切回前台整本重拉 | 不是容量墙，是等待时间和流量：3 万条（约 12 年）时一次约 8 MB、6 次分页 | 十年以上才明显 | 切回来要等几秒数字才更新；流量离每月 5 GB 还远。到时候做增量同步 |
| Supabase 数据库 | 500 MB（免费版，2026-10-05 官网核对） | 流水表连索引约 1 KB 一行 → 50 万行，两百年 | 写入被拒；要先撞上的反而是「连续一周没人访问就暂停」，每日备份就是为了这个 |
| 备份仓库 | 建议 1 GB | 每天一份全量 JSON，git 按差异存，一天只长几 KB | 几十年 |

所以现在**没有一堵墙在十年内**。设置页「本机缓存」那一格：分子是记账自己这本账的大小（按 UTF-16 算，偏大），
分母是浏览器报的整个网址的配额（`navigator.storage.estimate()`，和同一个网址下的交易日志共用，它的 IndexedDB `tj-journal`
也算在这份配额里，所以七成提醒只是个粗估）；浏览器不报配额（iOS 17 之前）就只显示占了多少。
