# 备份与恢复

> 2026-09-04 审查发现：这条路以前是**断的**——按当时的步骤恢复到新建的库，
> 一条都导不进去，而且报错还指错了地方。之所以三个月没人发现，是因为
> **README 里从来没写过恢复步骤，也就从来没人走过一遍**。

### 备份

设置页「导出 JSON 完整备份」。文件里 `amount` 是**整数分**（12.50 元存成 `1250`），
和内存里的表示一致；只有 `api.ts` 的 `txToRow` 会在写库前转成 numeric 字符串。

**写任何备份脚本都必须守住这条**：直接把数据库里的「元」倒进 JSON，恢复那天金额会
变成百分之一，而且数据库不会报任何错。`parseImport` 现在逐条卡 `Number.isInteger`，
就是这类错误的唯一防线（`src/lib/validate.test.ts` 锁着）。

#### 导出的是云端还是本机缓存？（2026-09-04 加）

导出取的是内存里那份快照。**本次打开 App 后一次都没同步成功过**的话（没信号、
Supabase 免费项目休眠、登录过期，或另一台设备记了账而本机没拉到），那份快照就是
本机缓存，可能比云端少几百条。拿它做「整库恢复」= 先删光云端再写回一份残缺的。

判据是 `store` 的 `loaded && !syncFailed`（`csv.ts` 的 `exportTrustworthy`）。
`cacheDegraded` 故意不参与：它说的是「写不进本机缓存」，而导出取的是内存快照，
只要这次同步成功过，内存里就是新的。

不可靠时**不禁止导出**（没网时想留个副本是正当需求），但会：

1. 弹确认框把风险说清楚，用户可以坚持；
2. 文件名带上 `-未同步`，例如 `记账备份-2026-09-04-未同步.json`；
3. JSON 里写 `"synced": false` 和 `"last_sync"`。**下次拿这个文件做整库恢复时，
   确认框会把这句话再念一遍**——三个月后没人记得当时有没有网。

老备份没有 `synced` 字段，读出来是「不知道」，不会被当成「不可信」去吓唬人。

### 两种恢复，别选错

| | 做什么 | 什么时候用 |
|---|---|---|
| **合并导入** | 同 id 覆盖，不删任何**行** | 误删了几笔想找回来。备份之后新记的账不受影响 |
| **整库恢复** | 先清空云端，再按文件重建 | 换了数据库，或者要完整回到备份那一刻 |

**「合并导入」有两个坑，出事那天优先选「整库恢复」**（已在内存版真 Postgres 上实测）：
- 它不删行，但会删**列的值**。文件里没有的列会被写成空——拿 `0003` 之前导的老备份合并导入，5 个分类的说明就没了。
- 备份之后改过账户名或分类名再合并导入，会撞唯一索引失败，报的是「已有同名的账户或分类」，让人摸不着头脑。它不丢数据（第一句就失败），但会卡住。

「合并导入」是 upsert，**只增不改删**——它做不到「撤销备份之后新增的记录」。
要回到某个时点只能用「整库恢复」。

### 换到新 Supabase 项目的完整步骤

1. 新建项目，Authentication → Users 建好自己的账号
2. SQL Editor 依次跑 `supabase/migrations/0001` → `0002` → `0003`
3. `.env.local` 换成新项目的 URL 和 anon key，`npm run deploy`
4. 登录 → 设置页 →「**整库恢复**」→ 选备份文件

第 4 步必须用「整库恢复」不能用「合并导入」：第 2 步的 `0001` 会预置 4 个账户和
全套分类，用的是**新 id**，而备份里是**旧 id 但同名**。`accounts` 有
`unique(user_id, name)`、`categories` 有 `cat_root_uniq` / `cat_child_uniq`，
`upsert(onConflict: 'id')` 不认名字这个唯一索引，一撞就抛 23505，第一句就炸、
后面全不执行。「整库恢复」先清空正是为了绕开这个。

### 整库恢复的两道保险（2026-09-04 加，这一节是重点）

以前的顺序是「粗查一下文件 → `wipeAll()` → `importAll()`」。粗查只看四样：
版本、id 是不是字符串、日期正则、金额是不是整数。数据库还有一大堆约束它不查，
于是**坏文件能通过检查、云端照常被清空、导入才失败——账本就没了**。
压测在真 Postgres 上复现过：喂一份「某条流水的分类 id 在文件里不存在」的备份，
那条流水被外键拒收，最后库里 `categories=1`、`transactions=0`。

**第一道：落地前把整个文件验完**（`src/lib/validate.ts`，纯函数，不联网）。
`supabase/migrations/` 里的约束在内存里先跑一遍，一条不过就整份拒绝，
**一个字节都不往云端发**。查的是：

| 类别 | 具体 |
|---|---|
| 列类型 | 三张表的 id 必须是 UUID；`sort` 在 smallint 内；`is_archived` 是布尔；`icon`/`note`/备注是文字；`created_at` 是合法时间 |
| 日期 | 正则过了还要**真有这一天**：`2025-02-30`、`2025-13-45`、`0000-00-00` 全拒，闰年按公历算 |
| 金额 | 整数「分」；绝对值不超 `numeric(12,2)` 能存的 ±9,999,999,999.99 元 |
| `tx_shape` | 收支必须有分类、不能有转入账户、金额 > 0；转账必须有两个不同账户、不能有分类、金额 > 0；校准必须有账户、不能有分类和转入账户（校准可以是负数或 0） |
| 外键 | 流水的 `account_id`/`to_account_id`/`category_id`、分类的 `parent_id`，都必须在**同一个文件里**找得到 |
| 触发器 | 分类的 `kind` 必须等于流水的 `type`；分类最多两级；父子 `kind` 一致 |
| 唯一索引 | 账户不同名；一级分类 `(kind,name)` 不重；二级分类 `(parent_id,name)` 不重；文件内 id 不重复 |
| 列本身 | 只保留数据库真有的那几列，多出来的键会让 PostgREST 报 `column does not exist`；老备份缺的列（比如 0003 之前没有的 `note`）按数据库默认值补齐 |

报错是人话，指到第几条、哪个字段、什么问题，例如
「备份文件第 37 条流水的日期是 2025-02-30，这一天不存在」。只报第一个。

**第二道：中途失败自动退回**（`store.ts` 的 `restoreSnapshot`）。
`importAll` 每 500 条一批、**不是事务**，校验再严也挡不住导到一半断网。
所以在 `wipeAll` 之前先把当前快照留在内存里，出错就立刻用它 `importAll` 写回去，
然后照实告诉用户：

| 情况 | 用户看到的 |
|---|---|
| `wipeAll` 第一句就失败（`api.ts` 给错误挂了 `step`） | 「云端一条数据都没删，账本还是原来的样子」——不回滚，也不吓唬人 |
| 清空后失败、退回成功 | 「你的账本已经退回操作前的样子，没有丢东西」 |
| 退回也失败 | 说清楚云端可能只剩一部分，**手机里那个备份文件先别删**，等有网再走一次，同一个文件重复导入不会变成两份 |

两条要记住的性质：

- 回滚是 **upsert，只覆盖不删**。故意的：恢复途中再去 delete，万一那步也失败，
  云端就真空了。代价是——如果要恢复的文件里有你现在账本没有的记录，
  失败前写进去的那部分会留下来，刷新后在明细里看得见，可以自己删。
- 回滚用的快照**来自云端，所以一定合法**（`test:db` 里有一条专门验它：
  把云端自己导出来的东西喂给校验器，过得去）。但它**不保证完整**：
  本次会话没同步成功过的话，它可能比云端少几条。所以恢复的确认框里也会提醒这一点。

### 为什么清空要分四步

`wipeAll()` 的顺序是 **流水 → 二级分类 → 一级分类 → 账户**：

- `transactions.account_id / category_id` 都是 `on delete restrict`，先删账户或分类会被拒绝
- `categories.parent_id` 也是 `restrict`，只删一级、留着二级同样会被拒绝

二级和一级分两步，是因为 PostgREST 每次调用只发一条带过滤条件的 `DELETE`，顺序得由我们显式写出来。

> 一处更正：早先这里写的是「`restrict` 不能延迟到语句结束再查，一条 delete 同时删父子会当场报错」。
> `npm run test:db` 实测**推翻了这句**——不带过滤的 `delete from categories` 把父子一起删是能成功的，
> 因为 `restrict` 的检查发生在**语句结束时**。它和 `no action` 的真正区别是能否延迟到**事务**结束。
> 分两步仍然保留：更显式、也不依赖这个细节。

### 这条路真的验过了

`npm run test:db` 会在内存里启动一个**真的 Postgres**（PGlite，Postgres 编译成 WASM），
真的执行 `supabase/migrations/` 下的建表脚本，再走一遍完整的备份与恢复。不联网、不碰任何真实数据。

实测结论：

| 场景 | 结果 |
|---|---|
| 换新库后直接「合并导入」 | ✅ 如预期失败：`23505 duplicate key ... accounts_user_id_name_key` |
| 「整库恢复」（先清空再导入） | ✅ 账户/分类/流水逐行逐字段完全一致 |
| 金额往返（分 → numeric → 分） | ✅ 零误差，含 4846.42、0.05、-10.84 |
| 误删几笔后「合并导入」 | ✅ 找回来了，备份之后新记的账没动，无重复行 |
| 同一个文件重复导入三次 | ✅ 幂等，条数不变 |
| 先删账户 / 只删一级留二级 | ✅ 都被外键拒绝 |
| 支出记到收入分类、转账两边同账户、三级分类 | ✅ 都被数据库自己拦住 |
| **12 条边界样本**（1 分、金额上限、负数校准、0 元校准、不指定账户的收支、转账、二级分类、同名二级分类、归档账户与分类、中文 + emoji + 引号 + 换行的备注、闰年 2 月 29 日） | ✅ 校验放行，wipe→import 后逐行逐字段完全一致 |
| **23 种坏文件**各走一遍完整恢复流程 | ✅ 全部在 `wipeAll` **之前**被拦下，云端行数一条没变 |
| 其中 22 种硬塞进 Postgres（第 23 种「同一个 id 出现两次」逐行 upsert 复现不了，单独一条测） | ✅ 数据库自己也确实拒收（证明规则不是编的；哪天 migrations 放宽了约束，这里会红） |
| 文件里同一个 id 出现两次 | ✅ 真实的批量 upsert 报 `ON CONFLICT ... cannot affect row a second time` |
| 导入到第二批（600 条流水）时断网，再用操作前的快照回滚 | ✅ 条数与内容一分不差地回到操作前，连已经被写坏的那 500 条也改回来了 |
| 把云端自己导出来的快照喂给校验器 | ✅ 过得去——回滚底稿的合法性有保证 |

动了 `supabase/migrations/` 或 `api.ts` 的导入导出，就手动跑一次 `npm run test:db`（约 60 秒）。
它**不在** `npm test` 和 `npm run deploy` 里，免得每次改代码都等。

### 自动备份（每天一次，2026-09-05 加）

**东西在哪**：私有仓库 `Michael-L340/jizhang-backup`，GitHub Actions 每天**北京时间 01:37**
跑一次，用你的账号登录 Supabase 把全量数据导成 JSON 提交进去。仓库必须是私有的——
里面是你完整的账本。这个仓库（公开的）里没有备份脚本，也没有任何密码。

**拿它怎么恢复**：仓库 `data/latest.json` 就是一份和设置页「导出 JSON 完整备份」
**格式完全相同**的文件。下载下来，直接走设置页的「整库恢复」（回到备份那一刻）或
「合并导入」（只找回误删的几笔）。不需要任何额外工具，也不需要懂 Git。

**五道闸，防的是「备份文件天天在更新，其实早就是坏的」**：

| 闸 | 做什么 |
|---|---|
| 非 2xx 即失败 | Supabase 的任何一个请求不是 2xx 就直接让这次 Action 红掉，绝不把半份数据当成功提交 |
| `count=exact` 对账 | 拉完之后再问一次数据库「你那儿到底有几行」，和拿到的条数对不上就失败 |
| 条数只许多不许少 | 比上一次备份**少**就拒绝提交（真删了一批账时手动放行）。防的是「云端被清空 → 备份忠实地把空账本存了下来 → 覆盖掉唯一一份好数据」 |
| 跨表引用闭合 | 每笔流水用到的账户和分类，必须在同一份文件里找得到。防的是「抓分类和抓流水中间你正好新建了一个分类」——三张表条数各自都对，文件却是恢复不了的 |
| 列集合断言 | 抓之前先看一眼数据库有哪些列，冒出脚本不认识的就拒绝。防的是最坏的一种：加了一列没同步改脚本，备份天天成功，恢复后那一列整列是空的，全程零报错 |

**设置页怎么看**：「每天自动备份」那一行。备份成功后脚本会把
`{ at, transactions, accounts, categories }` 写进 Supabase Auth 的 `user_metadata.backup`，
App 用 `auth.getUser()` 读回来（`api.ts` 的 `fetchBackupStatus`）。超过 **48 小时**
没备份就变黄并提示去看 GitHub Actions（`lib/backup.ts` 的 `backupHealth`）。

> 为什么读状态不用 `auth.getSession()`：那读的是本机存着的旧 JWT，metadata 是签发那一刻
> 烤进去的，服务端改了也要等 token 刷新才变——恰恰会在「备份停了」的时候显示「正常」。

**明确否决：前端不直接查 GitHub API**。这个 App 的构建产物部署在**公开**仓库的
gh-pages 上，任何塞进前端的令牌都等于公开发布，等于把那个私有备份仓库送人。
走 `user_metadata` 一个新令牌都不需要。

**它的自指局限（重要，别指望它挡住所有事）**：备份状态和账本数据在同一个 Supabase 库里。
所以它能告诉你「**备份没跑**」，但**告诉不了你「数据库没了」**——库要是整个消失，
状态也跟着一起消失，页面只会显示「还没有过自动备份」。它防的是 App 或数据的意外损坏，
不是 Supabase 账号本身出事。

**改密码要同时改两处**：设置页改完 Supabase 密码后，在电脑上跑 `npm run backup:password`
粘一次新密码（它就是 `gh secret set BACKUP_PASSWORD`，密码不经过任何文件），否则第二天起 Action 登录失败、
备份静默停摆（48 小时后设置页会变黄提醒，失败邮件也会到）。App 里做不到自动同步：改 GitHub 密钥需要令牌，
而前端代码包是公开的，任何令牌放进去等于公开。

**每季度手动导出一次**存本机或网盘。GitHub 账号本身丢了（被封、被盗、忘了密码），
代码和备份会**一起**没——自动备份和源码在同一个平台上，这是它唯一的单点。
另外：**没验过的备份等于没有备份**，第一次配好后照上面「换到新 Supabase 项目」的步骤
真的恢复一次。
