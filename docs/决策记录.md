# 决策记录

> 踩过的坑、明确不做的、用户偏好、开发历史。改代码前不必读，做决定前值得翻。

## 踩过的坑（按会咬人的概率排序）

1. **PostgREST 默认 max_rows = 1000**，全量拉取会被静默截断。后台已改 20000，`fetchAll()` 另有 `.range()` 分页循环兜底，两道都要留。
2. **时区差一天**。`new Date().toISOString().slice(0,10)` 拿到的是 UTC 日期，凌晨 0–8 点记的账会记到昨天。统一用 `date.ts` 的 `today()`（`Intl.DateTimeFormat('sv-SE', {timeZone:'Asia/Shanghai'})`）。数据库的 `date` 列不设 `default current_date`（服务器在 UTC）。
3. **浮点钱**。DB 用 `numeric(12,2)`，JS 全程整数分，只在 `money.ts` 两端转换。
4. **iOS `-webkit-overflow-scrolling: touch` 会把内部 `position:fixed` 困在滚动容器内**，底部弹层被导航条截断。已删掉该属性（iOS 13+ 默认惯性滚动），并把 `Sheet` 改成 `createPortal` 到 `document.body`。
5. **`#root` 设成 flex 居中后，与 app-shell 平级的元素会被挤成一条**。更新横幅曾因此在 iPhone 上点不到。现在 Root 统一渲染单列 `app-shell`，Shell/Login/Entry 都是 `flex-1` 子项。
6. **iOS 的原生 `<input type="date">` 不遵守 `max`**，能选到未来。已换成自绘 `DatePicker`。
7. **iOS 主屏 App 长期挂起，SW 不主动检查更新**。已加每小时 + 切回前台各查一次，设置页另有"检查更新"和"强制刷新（清程序缓存重载）"兜底。
8. **iOS 主屏 App 与 Safari 存储隔离**，同一网址要各登录一次。也因此不用 magic link，只用邮箱密码。
9. **下钻漏钱**：直接记在一级分类上（没选二级）的记录，下钻时会整个消失。已在 `byCategory` 里把这类归入「未细分」子项，并加单测守住"二级合计 = 一级合计"。
10. **WSL 下项目在 `/mnt/c`**，inotify 不工作，`vite.config.ts` 里开了 `watch.usePolling`。
11. **iOS 输入框 font-size < 16px 会自动放大页面**，全局已设 16px。
12. **Supabase 免费版无自动备份**，误删无还原点。靠设置页导出 JSON，建议每月一次。
13. **`upsert(onConflict: 'id')` 不认唯一索引**。表上除主键外还有 `unique(user_id, name)` 之类的约束时，同名不同 id 的行会直接抛 23505 而不是转成 UPDATE。备份恢复到新库整条路都栽在这上面，见第六节。
14. **`on delete restrict` 的检查发生在语句结束时，不是逐行立刻检查**。所以自引用表一条 `delete from categories` 把父子一起删是能成功的；它和 `no action` 的区别是能否延迟到**事务**结束。真正会被拒绝的是「只删一级、留着二级」。这条是 `npm run test:db` 实测出来的，此前文档里写反了。
15. **免费项目 7 天无访问会休眠**，数据不丢，需去控制台唤醒。

## 用户的偏好（沟通时注意）

- 编程小白。要大白话解释每个技术决定会带来什么可感知的后果，术语后面跟一句人话。
- 配置类工作全部由助手完成，用户只注册账号、临时生成令牌。令牌用完提醒删除。
- 强调模块化，"改一部分不影响其他部分"。除了分层，还靠类型检查、每页 ErrorBoundary、一功能一 commit 三道保险。
- 密码和账本数据绝不能进这个公开仓库；备份文件写到仓库目录之外（桌面）。

## 查证过、明确不做的

### 自动识别手机扣款（2026-09-04 论证，结论：iOS 上做不到，别再研究了）

用户问过「能不能自动识别手机扣款」。查证结果是**平台层面永久做不到**，不是我们代码的问题：

| 想做的事 | iOS 上行不行 | 依据 |
|---|---|---|
| 网页读银行扣款短信 | ❌ | 沙盒不开放，没有 API 也没有申请通道。Web OTP 只能取格式固定的验证码，Safari 还没实现 |
| 网页读微信/支付宝的付款通知 | ❌ | 同上，第三方看不到别的 App 的通知 |
| 从微信付款页「分享到」本应用 | ❌ | Web Share Target，WebKit 2019 年立的 bug（194593），2026-05 仍未实现。**安卓 Chrome 76 起支持** |
| 切回前台自动读剪贴板 | ❌ | 每次都要用户点页面 + 点系统的「粘贴」。安卓可授权一次后静默读 |
| 快捷指令「收到通知时」触发 | ❌ | iOS 26 的自动化触发器里没有这一项，只有「收到信息时」 |
| 靠银行短信兜底 | ❌ | 招行 2023-10 起信用卡提醒改走 App 推送不再发短信；中行 2024-05 起 500 元以下不发短信；微信零钱付款本来就不发短信 |

国内记账 App 钱迹的官方文档写得很直白：iOS 上的「自动记账」= 敲两下手机背面 → 截图 → 本地识字 → 用户确认。**这就是天花板，谁都一样。**

微信、支付宝的账单只能**申请后发到邮箱**（加密压缩包里的 CSV），微信一次最多 3 个月、支付宝最多 1 年，**都没有个人可用的 API**。银行导出的是 PDF 不是表格。用户评估后决定不做——每月要申请两次、收两封邮件、解压、选文件，共约 6 个动作。

### ⚠️ 如果哪天真要做账单导入，第一步必须是加「来源单号」字段

`transactions` 表现在**只有随机主键，没有任何字段记录这条记录从哪来**。后果很硬：
同一段账单不小心导两次，每条都是新记录，支出翻倍、余额多减一遍，
而且**事后无法分辨哪些是重复的**——两条长得一模一样，只能肉眼比对着删。

所以顺序是：**先加 `0004_*.sql` 存微信/支付宝的交易单号并加唯一约束，再写导入界面**。
写反了，等发现重复时已经晚了。注意这个字段要跟着走 7 个地方
（`types.ts` / `api.ts` 拉数据与导入 / `store.ts` 缓存 / `csv.ts` 备份格式与校验 / 测试夹具），漏一处的现象是「我的备份导不回来了」。

另外两个坑：**支付宝的导出文件是 GBK 编码**（微信是 UTF-8），微信前 16 行是说明第 17 行才是表头、支付宝前 24 行说明第 25 行表头；**退款在支付宝账单里算「不计收支」**，不会自动冲掉原来那笔支出；官方还提醒「快捷支付可能既产生支付宝交易也产生银行交易」——**三边账单不能都导**。

## v1.0.0（2026-09-05 截稿）

到这一版为止，「出事有后路、改动有护栏」这两件事都成立了，所以从 0.1.0 提到 1.0.0。
版本号显示在设置页底部。v1.0.0 之后每次 `npm run deploy` 自动把第三位 +1（v1.0.1、v1.0.2……可以到两位数），并打同名 git tag，`git tag` 就是发布历史；想确认手机上是不是最新版就看它。前两位只在大改时手动提。

**v1 包含什么**
- 记账：五大类支出用途 + 二级分类、收入、四个账户、转账、余额校准
- 账户余额：随时改成实际数字，之后的收支从新数字继续加减，反复改都对
- 白条 / 先用后付：下单记支出（账户选白条、填分几期），扣款时在账户页白条卡片上点「记这笔还款」（记成转账，不进收支）。欠多少、本月应还多少、到第几期都从这两种记录算出来，不用预排未来的流水
- 统计：分类饼图（可下钻二级）、收支趋势（按日/按月、五种时间范围）、账户余额曲线
- 数据：CSV / JSON 导出、合并导入、**整库恢复**
- 离线可看、iOS 主屏 App、多设备同步

**v1 的底线**（这些是花了一整天验出来的，不是声称的）
- 「整库恢复」在真实数据上验过无损：导出 → 恢复 → 再导出，按 id 排序后整份哈希相同
- 坏备份**在清空云端之前**就被拦下（37 条校验，23 种坏文件实测全部拦住、云端一行没动）
- 导入中途失败会自动退回操作前的样子
- 没同步成功时导出的文件，文件名和内容里都带「未同步」标记
- 309 项测试（234 常规 + 75 在内存版真 Postgres 上跑），每一条都做过变异验证

**v1 明确不做的**：自动识别手机扣款（iOS 上永久做不到，见第十节）、账单导入、预算、
标签、附件、多人共享。

**已知未覆盖**：页面层没有自动化测试（node 环境没有 DOM），页面行为靠真机确认。

## 还没做的

### 排在最前面的两件（2026-09-05 用户拍板）

~~**1. 离线记账**（优先级最高）~~ **已完成（2026-09-07）**。断网时记的账进「待上传队列」（`lib/outbox.ts`），联网后自动补传。设计要点：

- 队列只存**最终状态**（`Map<id, 记录 | 已删除>`），不存操作流水。断网时记一笔再改两次再删掉，队列里始终只有这个 id 的一条，补传按最终状态 `upsert` 或 `delete`，不用回放顺序，重复执行也安全。
- 结构和 `lib/pending.ts` 的在途补丁表**故意一致**，因为都要靠 `applyPending` 叠到服务端快照上。但寿命不同：补丁表 60 秒过期、只在内存；队列传成功才删、写进缓存跨会话。`refresh()` 里两层叠加，队列在最上面。
- 失败分两类，由 `api.isPermanentError` 判定：带 `23xxx`/`42xxx` 错误码 = 数据被拒，回滚并报错；其余（没网、超时、登录过期）一律进队列。**默认可重传**，因为误判成永久失败是当场丢账，误判成网络问题只是队列里卡一条、用户看得见。
- 补传成功后只删「刚传的那一版」（`outboxTx.get(id) === v`）。等响应的几百毫秒里这条可能又被改过，无条件删会让云端停在旧值、界面停在新值、队列还空了。
- 退出登录会清空队列（换账号后补传过去是灾难），所以退出前会提示还有几笔没传。整库恢复不清队列，但会在确认框里说明「最终结果是备份 + 这几笔」。

**2. 多币种**（以后加，不是现在）。用户明确要求：**各币种分开算，不换算成同一个货币**。这个口径让它简单得多——不需要汇率表，也不用回答「总余额按哪天的汇率算」。做法是账户上挂一个币种字段，合计按币种分组显示。真正的成本在「加数据库字段要同时改三处」那条规矩（见 CLAUDE.md），以及所有显示合计的地方都要改成「一组数」而不是「一个数」。**现在不提前埋字段**——埋了每次改动都要多背一个没人用的包袱。



预算、微信/支付宝账单导入、自然语言记账、周期账单、搜索、标签、邮件找回密码。

统计页还有一批 09-05 换暖色主题之前留下的写死颜色：趋势线用旧的支出红 `#e5484d` / 收入绿 `#1f9d55`、余额线用旧品牌蓝 `#2f6fed`、坐标轴是冷灰。它们和分类配色无关，但主题变了不会跟着变。收拾时把 `Stats.tsx` 加进 `palette.test.ts` 那条「不许写死颜色」的断言里（首页已经在里面了）。
